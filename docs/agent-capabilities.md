# Agent capabilities: browser, vault, collaboration (2026-11-08)

Design record for the capability release that lets Ghosts act on real websites, use the owner's credentials without seeing them, and collaborate with fewer owner interruptions. [Architecture](architecture.md) keeps the principles; this document records the decisions and contracts behind them.

## Decisions

| Area | Decision | Rejected and why |
|---|---|---|
| Browser engine | [vercel-labs/agent-browser](https://github.com/vercel-labs/agent-browser) (Apache-2.0, Rust CLI, already pinned by the owner's `agent-ui` at 0.41.2) driving the installed Google Chrome | Playwright MCP/CLI: origin filters are explicitly not a security boundary. chrome-devtools-mcp: no secret path, URL patterns only. browser-use / Stagehand: an LLM inside the primary interface. Lightpanda: AGPL, no persistent login, no visible window. OxiBrowser (owner's engine): its Ghost lane contract fits, but it claims no production-site compatibility, has no screenshots and keeps no login; Korean sites (Korail, 정부24, 쿠팡) need Chrome. |
| Network containment | A host-owned egress proxy. Chrome gets `--proxy-server=<proxy>` and `--proxy-bypass-list=<-loopback>`; the proxy resolves each destination, refuses loopback, private, link-local, CGNAT, ULA, multicast, NAT64/6to4-embedded private addresses, `localhost`, `*.local`, `*.internal`, `*.ts.net`, fails closed on unparsable addresses, and connects to the address it checked (no DNS rebinding). WebRTC is the one path around an HTTP proxy: review showed `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` alone still let a page send STUN to `127.0.0.1` over UDP, so a host init script removes the WebRTC constructors in every frame and the flag stays as a second layer. Spike: navigation and page `fetch()` to `127.0.0.1`/`localhost` were refused while `https://example.com` loaded. | agent-browser `--allowed-domains`: an allowlist, cannot express "public internet", and is incompatible with saved login state. An outer `sandbox-exec` profile around Chrome: not attempted in this release; Chrome applies its own seatbelt sandbox and nesting was not validated. |
| Sessions | One agent-browser session per conversation (own tabs and refs), `--restore ghost-<id>` per Ghost (cookies and storage shared by that Ghost's conversations, last writer wins), encrypted with a host key. The child runs with `HOME=<root>/browser/home` and a namespace, so the owner's own agent-browser state and plugins are never read. | One shared session per Ghost: concurrent conversations would fight over tabs. |
| Approvals | By blast radius. Reads and ordinary page actions run and are journaled as effects. `browser_propose` (purchase, payment, sending a message, deleting, legal submission) and every card-field fill open an `approve_effect`; the host performs the click or fill only after approval, only if the page URL is unchanged and the element still has the role and name the owner saw. Host commands keep their own approval. As defense in depth, `browser_click` and Enter/Space presses on an element whose accessible name looks like pay, order, delete, send, submit and their Korean equivalents are refused with a pointer to `browser_propose`; this name guard is a heuristic, not a payment authorization boundary. The real money boundary is that card values exist only in the vault and every card fill needs approval; a site's own stored payment method behind a renamed button remains a residual risk. Since 2026-11-10 the host also reads page facts itself (`FACTS_SCRIPT`: checkout/payment URL or text signals and the shown total): on a checkout step every click and Enter/Space is refused toward `browser_propose` whatever the button is called, unreadable facts count as a checkout, and an approval carries the merchant and total the host read; the executor re-reads both right before the click and refuses if the site or total changed. A page can still hide these signals, so this narrows the residual risk rather than closing it. | Per-click approval (unusable); confidence scores (the model controls them). |
| Secret exposure after a fill | Fill values travel only over stdin and are registered per browser session (memory only): later text results redact the value and its URL-, form-, HTML- and JSON-encoded forms. After a card or secret-value fill, screenshots are refused until the session closes; after a password fill, until that tab's URL changes. A password goes only into a password field; login and secret fields only on the item's exact origin, never in frames. | Persisting a redaction list (would store secrets). |
| Vault | A Ghost-owned vault ported from Shade's core model: kinds `login`, `card`, `contact`, `secret`, `api`; canonical https origins (Shade `normalize_origin`); generated passwords (Shade `generate`); encrypted version history; Apple/Chrome CSV import; TOTP seeds. AES-256-GCM per item under a host key at `<root>/vault/key` (0600); store at `<root>/vault/vault.db`, outside the ledger and its event feed. Secrets are write-only. Grants are per Ghost. | Calling Shade's CLI: whole-vault grant only and values returned to the caller. Shade stays a separate app for later. |
| Secure form | `vault_request` opens a `question` decision with `proposal.secureForm`; the owner answers in the app's secure form, which posts to the vault API. The ordinary answer path refuses these decisions for every principal, so a value can never be typed into chat. The iPhone hosts the same web UI, so it answers through the same secure form. | A new decision kind: clients decode kinds strictly and a native form would duplicate the web UI. |
| Handoff | `browser_handoff` opens a `question` with `proposal.browserHandoff.live` and holds off Ghost browser calls until the owner answers. The owner uses the same live browser panel from the Mac or a paired phone; after the answer the Ghost takes a fresh snapshot and continues on the page the owner left. A Mac-window handoff closes and resumes headlessly. Owner frames are not model screenshots: they show the owner's page without model redaction. | The earlier 1.5-second screenshot polling path is replaced by the authenticated live stream below. |
| Collaboration | A child asks its delegating Ghost first (`ask_parent` → parent `answer_child`); only the parent escalates to the owner. Reviewer verdicts carry `evidence` and `scope`; `revise` sends both. A delegate may give its child deterministic `checks`: for a child they gate review (fail → revise without review, pass → review); for a root Work owner checks still decide. Revision history travels with the outcome report so the parent or origin conversation can retain the lesson. | A peer messaging channel; automatic memory writes. |
| Goals | Since 2026-11-11, the team keeps up to three long-term goals. A goal is a direction with boundaries, never a quota or deadline, and grants no capability. The owner writes one or adopts the main's `goal_propose`, an owner-only `question` (no recommendation, so no main or timeout settlement). The main keeps a short milestone line under each; finishing one needs an accepted linked Work. [Team goals](architecture.md#team-goals). | A goal hierarchy deeper than goal → milestone → Work, a scheduler or wake budget per goal, progress percentages, main-adopted goals. |
| Desktop control | `ghost.desktop` combines agent-desktop 1.2.0 accessibility actions with Geist 0.5.0 window capture and physical input. Both run under Developer ID-signed `Ghost Control.app` (`dev.projectoxi.ghost.control`), which becomes its own responsible process and registers with LaunchServices before TCC checks. The owner grants Accessibility and Screen Recording to that identity. Tools are explicit grants and also require `hostExecution`. | Giving TCC access to a changing bare Host path; silently substituting pointer input for a failed semantic action. |
| Shared host guard | The host/IP guard moved from `web.ts` to `integrations/netguard.ts`, shared by `web_read`, `reach` and the egress proxy. Moving it fixed an IPv6 expansion bug: `::1` and IPv4-mapped loopback (`::ffff:127.0.0.1`) were misclassified as public. | — |
| Live browser (2026-11-11) | Owners and paired devices drive the same session over authenticated NDJSON, with at most four viewers. Obscura supplies native damage-driven JPEGs. Chrome uses a private, target-scoped `Page.captureScreenshot` channel clipped to the CSS viewport; daemon frames only trigger damage. This avoids macOS's minimum physical-window size producing incorrectly labelled phone frames. Capture is single-flight, coalesces the latest damage, and respects the active viewer FPS. The UI enables input only after a matching JPEG decodes. Owner input invalidates model refs. | Polling, relabelled or stretched pixels, and a third-party Tauri webview outside the Host proxy/login boundary. |
| Owner takeover and Mac window | Obscura remains viewable natively. The first owner-control gesture promotes it to headless Chrome and is discarded, not replayed; `browser_handoff` promotes before asking. **Mac 창으로 열기** opens headed Chrome. Only cookies, URL and viewport transfer from Obscura, not page DOM or local storage; existing Chrome storage remains. The session stays Chrome. | Obscura has no native window and its shared-runtime contexts cannot authenticate credential capture. |
| Login capture | A Chrome isolated world authenticates page/context and field metadata; save authority comes only from bytes actually edited through Host owner controls or genuine native input. There is no DOM-value fallback and model actions cannot create login candidates. A top-level HTTPS username/password pair is saved only after observed form disappearance or navigation; closing a window alone is insufficient. The owner receives a notification without the password, and the Ghost receives the item id. Values remain private and registered for redaction. | Page-provided values/events, Obscura shared-runtime capture, and treating CAPTCHA/CVC/OTP fields as passwords. |
| Whole-card fill | `browser_fill_card` fills number, expiry (or month/year inputs and selects), CVC and name after one `approve_effect` that shows merchant and total read by the Host; `browser_fill_secret` no longer takes card fields. | One approval per card field (four cards per checkout). |
| Message codes | `host_message_codes` reads recent incoming verification codes from `~/Library/Messages/chat.db` through a read-only SQLite connection, including committed WAL rows. Text comes from `message.text` or the first `attributedBody` NSString. Verification-specific context is required; bulk-SMS markers and postcodes do not qualify. Explicit host-tool grant and Full Disk Access are required; SMS also need iPhone Text Message Forwarding. | `immutable=1` ignores WAL; separately copying a live DB and WAL cannot guarantee consistency. If SQLite admission fails, the tool reports the permission/restart prerequisite instead. |
| Mail client | Owner-registered IMAP/SMTP connections (app passwords, or Outlook OAuth2) are browsable in the app's 메일 view and usable by Ghosts granted `mail_*` tools. OAuth access refresh runs before transport authentication; access-token rotation preserves the account epoch and existing send approvals, while account changes and revocation still block sending. Reads use `BODY.PEEK`; flag/move/archive/trash are journaled; every Ghost send waits for the owner's approval showing recipients and the whole body, and an uncertain send is never repeated. Mail tools are not in a new Ghost's default allow-list. The empty mail view opens the shared account-first connection settings. | Invented OAuth client identities; bypassing provider app-password policies; using a Google API token as a Gmail IMAP/SMTP grant. |
| Service API keys (2026-11-11) | Owner question "API 자격증명은 금고를 확장하는 게 낫지 않나": yes. Kind `api` holds an exact https origin, an optional client/key ID (`username`, plain metadata) and the secret `value`. It reuses the vault's per-Ghost grants, secure form, encrypted history and backup. Only Host integrations read it (`Vault.apiCredential(ghostId, origin)`, exactly one granted item per origin); `reveal`, and with it `browser_fill_secret`, refuses `api` items, so the key never reaches a page or a model. | Host `secrets/` files: global to the Host, no per-Ghost grant, no owner UI. Reusing kind `secret`: it is page-fillable at its origin and holds one value. |
| Toss Securities (2026-11-11) | `toss_read` reads the owner's [Toss Securities Open API](https://openapi.tossinvest.com/openapi-docs/overview.md) through the granted `api` item for `https://openapi.tossinvest.com`. The same Toss key can trade, so the boundary is the client: it sends only `GET` to an allow-list of the spec's read routes (accounts, holdings, transactions, orders, buying power, market data); order creation, modification and cancellation are POST/DELETE routes it cannot express. Toss keeps one valid token per client (issuing another revokes the first), so tokens are cached in memory per client ID, bound to the digest of the exact secret that issued them, and shared by every call holding that credential; the vault is read again before each token use, so an edited, rotated or deleted-and-recreated key never receives another key's token. A revoked or expired token is re-issued once. Calls come from this Mac, so its public IP must be in the key's 허용 IP list; using the same key elsewhere revokes Ghost's token and the reverse. Not in the default tool set: holdings and transactions reach the Ghost's model provider. Codex review (2026-11-11) found token reuse across a deleted and recreated item id (P1) and stale-credential refresh (P2); both fixed by this keying. | A generic HTTP tool with the key (the model could reach order routes); per-endpoint tools (40 GET routes, one shape); caching by vault item id and revision (ids can be reused after deletion). |

## Model-facing tools

The Apple Silicon Host can ship Obscura as a second browser. Choose
`browser_open { url, engine: "obscura" }` for a conversation's first browser
open. Close the session before selecting a different engine. The Host starts
the official binary under a macOS sandbox with an authenticated loopback CDP
listener and network access to the Host proxy port. Obscura supports the app's
live browser handoff. Its sessions are memory-only and require a fresh login
after closing or expiry. For vault input the exact HTTPS origin must appear
in `browser.obscura.loginOrigins` in addition to the existing Ghost and vault
grants. The Obscura route accepts login fields. Use the existing browser for
cards and file transfers.

All browser and vault tools are selectable and part of the default allow-list for new Ghosts; host, desktop, mail and finance tools stay explicit. Page-derived text is untrusted evidence and is wrapped in agent-browser content boundaries.

## Owner API (vault)

Every authenticated principal (owner token and paired devices); values are accepted, never returned.

| Route | Body / result |
|---|---|
| `GET /api/vault/items` | `{ items: VaultItem[] }` (expired one-time items are pruned) |
| `POST /api/vault/items` | `{ id?, kind, title, origin?, username?, password?, totp?, card?: {number, expiry, cvc, name}, contact?, value?, hints?, ghostIds? }` → `VaultItem`. `api` takes `origin` (required), `username` (client ID) and `value` |
| `PATCH /api/vault/items/:id` | same fields, omitted = unchanged; `password`/`totp`/`card`/`value` replace and keep the previous version encrypted |
| `DELETE /api/vault/items/:id` | removes the item and its history |
| `POST /api/vault/import` | `{ csv }` (Apple Passwords or Chrome export) → `{ imported, skipped, rejected }`. Imports https logins with their username, password and a valid Apple `OTPAuth` seed; identical origin+username+password rows are skipped, a different password for the same login is kept as its own item. Notes and unknown columns are not imported (Ghost has no recovery-source archive like Shade's) |
| `POST /api/vault/requests/:decisionId` | secure-form answer: item fields + `save: boolean`; resolves the decision with metadata only. `save:false` makes a one-time item that expires after 24 h |

All routes use the existing bearer authentication for the owner and paired devices. Responses and streams are `no-store`.

| Route | Purpose |
|---|---|
| `GET /api/browser/sessions` | active session identities, engine, Mac-window state and pending handoff decision |
| `GET /api/browser/sessions/:conversationId/live?fps=8` | NDJSON stream of JPEG frames, page metadata and session end; 1–15 fps, at most four viewers |
| `POST /api/browser/sessions/:conversationId/input` | one validated mouse, key, text or navigation event |
| `POST /api/browser/sessions/:conversationId/window` | visible Mac Chrome; an Obscura session migrates with cookies |
| `GET /api/mail/accounts` | configured mail accounts with credentials |
| `GET /api/mail/:connectionId/mailboxes` | mailbox paths, special-use roles and counts |
| `GET /api/mail/:connectionId/messages?mailbox=&q=&before=&limit=` | newest-first UID pagination, up to 100 per page |

## Storage and operations

- Ledger migration 6 adds `work_questions` and a revision history column on `works`; the vault is a separate file. A previous Host refuses ledger 6, so rollback after cutover needs the pre-cutover backup.
- Card-fill authority is a transactional data-only startup cutover, marked once by `settings["browser:card-fill-cutover:1"]`: a Ghost, Work scope or Activity with `browser_fill_secret` also receives `browser_fill_card`; unrelated or empty allow-lists do not. Later owner revocation is preserved on restart. This avoids renumbering unrelated schema migrations on concurrent release lines. Pending old per-field card approvals are declined and must be proposed again as a whole-card fill. `/browser-vault-2` in the update storage fingerprint prevents automatic rollback to an older client that cannot preserve the new contact fields.
- Config: `browser: { executable, chrome?, idleTimeoutMinutes?, obscura?: { executable, loginOrigins? } }`. Without it the browser tools are left out; the vault has no config. Obscura receives only a private cached copy of the Mac's `AppleSDGothicNeo.ttc` via `--font-dir`, with a narrow read-only sandbox grant; this supplies Korean glyphs without loading all system fonts or distributing Apple's font.
- Native browser releases build upstream 0.41.2 commit `d52a5e90c372ec4710c69adc3837ac14bbd852aa` from archive SHA-256 `d210044290de66829e8170e0eef690c510c249e0719113f53df4ed239714bfa3`, applying `apps/ghost-host/scripts/agent-browser-input-target.patch`. The real dashboard uses frozen pnpm dependencies and Rust uses `Cargo.lock`; the root prebuilt-binary download is disabled. The release signs and manifests the compiled binary, not the official unpatched download. Connected-target and focus checks fail closed before text insertion, including shadow roots and accessible frame owners, without requiring OS-window focus; later arbitrary page-driven focus changes are not locked out.
- Snapshot redaction preserves only producer-attributed renderer structure and validated native ref metadata. `snapshotAttribution.version = 1` supplies sorted UTF-16 ranges; page names, values and URLs are never attributed. Secret matches are found across the original full string, so injected ref-looking text and matches spanning structure cannot bypass masking. Missing or malformed attribution fails closed after private values enter the session; arbitrary eval output never gains a protocol exemption.
- Owner input in unknown fields, child frames, closed shadow roots and contenteditable surfaces contributes privacy protection, never login authority. Segmented numeric entry blocks screenshots and conservatively masks numeric reads; private-world startup buffers are bounded and honor the captured input mode. Sticky screenshot denial runs before observer I/O. A dead private observer fails closed instead of silently accepting reads.
- Live rendering requests fresh pixels after deferred owner-metadata capture releases its busy scope. An input error revokes stale dimensions and reconnects the stream without replaying the input; touch drafts and focus survive, but submission waits for a matching decoded frame.
- PC control is detected beside the release executable (`Ghost Control.app`, `agent-desktop`, `geist`). Explicit development config is `desktop: { control, agentDesktop, geist }` with absolute paths; `desktop: null` disables it. Settings › team › Ghost settings exposes **PC 조작**, separate from the default tool set. It also requires **PC 직접 실행**. Screen text and images can reach the Ghost's configured model provider; this is owner-account access, not a browser-style network or secret sandbox.
- Desktop runtime state is private to `<root>/desktop`. The Host serializes commands; semantic actions do not move the pointer. Physical actions require a fresh screenshot and share the owner's pointer and keyboard. Windows on another Space are not forced forward. Ghost's own app and password-store apps are excluded; these exclusions and the high-impact label guard do not contain an agent already granted owner-account PC execution.
- Each helper uses a private APFS-cloned Geist executable under `<root>/desktop/runtime/geist-*`, because Geist keys its worker IPC to the executable identity. Separate Host roots cannot stop each other's workers. A confirmed clean shutdown removes that clone; an unconfirmed or forced stop retains it for recovery, and the next helper uses a new clone.
- Both keyboard paths refuse quit, logout, lock, Force Quit and Empty Trash shortcuts across modifier aliases and token order. Geist does not report field focus, so a capture containing any protected field blocks physical keyboard input; a protected last accessibility target also blocks it even when the image tree omits that field. Use semantic actions on non-secret fields or let the owner handle a protected form.
- Font-cache startup recovers interrupted `.font-<uuid>` / `.source-<uuid>` staging files only when they are regular, single-link files owned by the Host's Unix user with the producer's expected permissions. Symlinks, hardlinks, unrelated entries and unsafe modes remain startup errors; completed font/fingerprint files must still be 0600.
- `ghost backup` copies `vault/vault.db` (consistent `VACUUM INTO`, integrity-checked) and `vault/key` when present. Browser login state under `<root>/browser` is not backed up: losing it only means signing in again.
- Browser files: uploads are copied with no-follow reads from the Work workspace into `<root>/browser/staging` (≤ 32 MiB each) and Chrome reads only the staged copy; downloads land in `<root>/browser/downloads/<session>` (≤ 64 MiB and 32 files per session) and are copied into the workspace with no-follow, create-only writes. Screenshots are read into the result (≤ 8 MiB) and deleted. Staging and downloads are removed when the session closes and at host shutdown.

## External prerequisites

- [Obscura v0.2.6](https://github.com/h4ckf0r0day/obscura/tree/v0.2.6#rendering) includes native screenshots and screencasting in the pinned rendering archive. Its independent layout/Web APIs differ from Chrome; a visible Mac window transfers cookies to Chrome rather than pretending Obscura has a native window. Its named “isolated” contexts [share the page's V8 runtime/global](https://github.com/h4ckf0r0day/obscura/blob/v0.2.6/crates/obscura-cdp/src/domains/runtime.rs#L627-L629), so they are not a credential-capture trust boundary.
- [Apple Text Message Forwarding](https://support.apple.com/en-us/102545) must send SMS to this Mac. Messages access additionally needs the owner's Full Disk Access grant for the running Host; a tool grant cannot bypass macOS privacy permissions.
- Gmail and iCloud connections use provider-issued app passwords, not the owner's main password. [Google](https://support.google.com/accounts/answer/185833) requires 2-Step Verification; organization policy, security-key-only setup or Advanced Protection can make app passwords unavailable. [Apple](https://support.apple.com/en-us/102654) requires two-factor authentication. These accounts cannot be connected by bypassing their provider policy. Outlook OAuth uses the owner's registered client and IMAP/SMTP scopes. The separate Google OAuth connection requests identity and optional Drive access, not Gmail IMAP/SMTP authority; that would require `https://mail.google.com/`. Account setup stays in the app's write-only connection form.
