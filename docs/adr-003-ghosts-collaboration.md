# ADR 003 — Ghost core, local collaboration protocol, Ghosts management

Ghost remains one independent durable identity. Ghosts is a new application layer managing multiple Ghosts and their shared tasks. They live in this repository with three boundaries: existing identity/activity/policy core; a versioned local delegation envelope; coordination and a read-only JSON management snapshot. Existing Knock, FARM and Garden projects remain untouched.

The inspiration from dots is limited to observable conversation, follow-up questions, delegation and status lookup. This ADR makes no assertion about dots internals. Public A2A/MCP and durable-execution research will inform later compatibility decisions; this first protocol is explicitly local and does not claim A2A/MCP compliance.

The next unit accepts one parent request and exactly two workers. Each assignment persists profile UUID, role, stable delivery/message id, parent/root/delegation lineage and a `text_only` capability ceiling. Roles are assignment context, not permission grants; worker persona and existing policy remain independent. A delegated activity cannot acquire filesystem, HTTP, shell, MCP, finance or other capabilities from its prompt or its parent.

A local Ghosts SQLite journal owns parent/assignment/result records and its own writer lock. Each Ghost still owns its profile SQLite inbox/outbox/tasks. There is no cross-database transaction claim: record intent first, submit using a stable receiver message id, recover with deduplication, harvest correlated results, and retain ambiguous worker outcomes as uncertain without automatically rerunning them. Completion requires both successful child results; failure and uncertainty keep partial results visible.

Worker execution must target only its delegated task. A coordinator must never drain unrelated queued tasks or overwrite another worker's identity/policy. Cancellation is durably recorded at the parent before bounded child propagation; pending cancellation is reconciled on a later explicit run without starting new work. A restarted running worker uses the existing core's uncertain recovery rule.

Management is a read-only JSON snapshot behind the CLI for this unit. It uses actual persisted coordination and worker outcomes, not synthetic UI data. No UI server, automatic daemon, scheduler, credential setup, quota workaround, financial actions, remote publication or deployment are part of this work.

Development is capped at three ordinary OMP CLI requests (one implementation and up to two diagnostics-driven repairs), each with a 12-minute limit, automatic retries/fallback disabled and model tools disabled. Quota freshness is unknown; no quota query is retried through this task. A blocked authentication/quota response stops further provider attempts. All runtime tests use mock providers and `-j1` builds.

## Public research received from parent

A2A 1.0 is a vocabulary and future boundary reference, not this unit's engine. Its [SendMessage idempotency](https://a2a-protocol.org/v1.0.0/specification/#331-idempotency) is optional; [messages and artifacts](https://a2a-protocol.org/v1.0.0/specification/#37-messages-and-artifacts), streams or history do not replace the local durable inbox/outbox. [a2a-rs](https://github.com/a2aproject/a2a-rs) supplies protocol/types/transport, while [rmcp](https://github.com/modelcontextprotocol/rust-sdk) supplies a future tool/context boundary. No dependency on either is added here, and per-server Node/Python dependencies cannot become Ghost's implicit runtime requirement.

The parent investigation also references [transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [SQLite WAL](https://sqlite.org/wal.html), [private discovery](https://a2a-protocol.org/latest/topics/agent-discovery/#3-direct-configuration-private-discovery), and [Tauri's process model](https://v2.tauri.app/concept/process-model/). These inform future transports and UI; they do not change the bounded local implementation scope.

The host separates ghost_id, session_id, task_id, attempt_id and process_instance_id. A provider session is adapter metadata; canonical conversation, tool results and compaction checkpoints will belong to Ghost storage in a later unit. Worker conversations are separate, with no global shared conversation. The sender/message dedup key is namespaced when handed to the existing profile inbox, preserving the original standalone task API.

The parent task owner is an existing Ghost, and the host validates its persisted identity rather than trusting a claimed sender in model text. The parent owner is responsible for aggregation. Artifact metadata records producing task, owner/worker identity, media type, content hash and lineage provenance. Roles or advertised capabilities never establish authority. The v1 text-only ceiling is restricted to the recipient and this delegation while the parent is active; resource/operation/expiry grants for richer tools are deferred rather than silently inherited.

Management clients use the public local snapshot API and cannot edit databases or become the sole owner of execution state. This unit exposes that API through a CLI without opening a listener. A future first process transport must be a private Unix socket or authenticated loopback. Process separation alone is not an OS sandbox. Deterministic SQLite fault injection plus close/reopen will exercise lost-ACK and interrupted-parent recovery windows; a true socket kill/reconnect/event replay test requires that later transport and is not claimed here.
