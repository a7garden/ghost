# Ghost 실행 기반: 실패 원인, 품질 체계, 업무 범위

상태: **제안** (2026-11-12 작성). 측정한 실패 원인과 품질에 관한 근거를 담는다. 구현 기준은 [기반 설계](ghost-infrastructure.md)다. 2~4절의 원인과 실행 기반은 그 문서가 코드로 가져가고, 5~7절의 규칙과 업무별 구조는 코드가 강제하지 않는 권장 구성이다(2026-11-12 소유자 결정: 조직과 내부 구조는 사용자가 꾸린다). 채택 전까지 정본은 [architecture](architecture.md)와 [current-priorities](current-priorities.md)다. 코드는 바꾸지 않았다.

질문: 맡긴 일이 왜 실패하는가. 컨테이너는 필요한가. 담당 하나의 판단에 걸리는 품질 한계를 어떻게 넘는가. 생활 도움, 글과 영상과 연재, SNS 운영, 전문 개발까지 한 기반으로 할 수 있는가.

## 1. 결론

1. **실패의 가장 큰 원인은 모델 한도 소진이다.** 모델에 보낸 제출의 28%가 사용량 한도 오류로 답 없이 끝났고, 실패한 맡긴 일의 63%가 그 영향을 받았다. Host는 한도를 자원으로 관리하지 않는다.
2. **한도의 큰 몫이 소유자 요청과 무관한 차례에 쓰인다.** 직접 대화가 모델 차례의 29%, 입력 토큰의 41%를 쓰는데 소유자 메시지는 78건뿐이다. 자율 깨움과 결정 검토가 계속 길어지는 대화에 쌓여 차례마다 평균 19.6만 토큰을 읽는다.
3. **마감은 일하지 않는 시간까지 센다.** 마감 실패 63건 중 37건은 소유자의 결정을, 8건은 하위 일을 기다리던 중이었다. 18건은 이미 끝내고 수용을 기다리던 일이다.
4. **컨테이너는 목적에 맞지 않게 쓰이고 있다.** 과업끼리의 오염을 막으려던 것인데, 도구도 프로젝트 파일도 네트워크도 없는 빈 Ubuntu에서 Perl로 일하게 만들었다. 정작 오염이 생기는 Mac 직접 실행 56건은 워크트리를 한 번도 쓰지 않았다. 기본 환경을 Mac의 작업 공간으로 바꾸고 컨테이너는 받은 코드를 돌릴 때만 쓴다.
5. **담당의 한계는 일마다 계약과 독립 평가를 두고, 실패한 것만 등급을 올려 넘는다.** 담당과 평가는 가장 강한 모델이 맡는다. 실행은 일의 모양에 따라 싼 모델에 나누거나 강한 모델이 직접 한다.
6. **협업의 단위는 직무가 아니라 기능이다.** 계획, 실행, 조사, 평가, 자문. 쓰기는 한 줄기, 읽기는 병렬, 평가는 독립.
7. **업무 범위는 코드가 아니라 문서 구조로 넓힌다.** 정본(무엇이 진실인가), 기준(무엇이 좋은가), 채널(어디로 내보내는가), 리듬(얼마나 자주)을 범위의 문서로 적으면 코드 저장소, 연재 소설, 영상 채널, SNS 계정, 생활 대행이 같은 고리 위에서 돈다. 이 네 가지는 권장하는 구조이고 코드에 있는 필드가 아니다.
8. **지금 사람을 대체할 수 있는 범위는 검증이 싼 일이다.** 가장 강한 모델이 실제 프리랜서 과업의 41%를 고객이 받을 수준으로 끝낸다. 플래시급은 5~10%다. 판단과 취향은 소유자의 기준을 기반이 넓히는 방식으로만 다룬다.

## 2. 실행 실패의 실제 원인

운영 Host의 원장과 대화 저장소, Host 로그를 읽기 전용으로 조회했다. 기간은 2026-11-07부터 11-12까지다.

| # | 원인 | 측정 | 코드 위치 |
| --- | --- | --- | --- |
| R1 | 모델 한도 소진을 실패로 처리한다 | 제출 2,246건 중 665건이 답 없이 끝났고 그중 619건이 429 한도 오류다(`Token Plan usage limit reached` 597건). 맡긴 일 대화 248건, 자율 깨움 98건, 결정 후속 69건, 검토 69건이 사라졌다. 실패한 맡긴 일 95건 중 60건, 마감 실패 63건 중 39건, "멈춤" 실패 12건 중 9건이 한 번 이상 맞았다. 완료된 139건 중 61건도 맞았으므로 한도 오류가 곧 실패는 아니다. 대체 모델 전환은 585회 일어났고 대체 모델도 소진됐다 | `engine/index.ts`의 제출은 `unanswered`를 그대로 끝낸다. 한도와 재개 시각을 아는 곳이 없다 |
| R2 | 길어지는 대화에 깨움을 쌓는다 | 6일간 입력 28.7억 토큰. 직접 대화 11.9억(41%, 차례 6,042), 맡긴 일 16.3억(차례 13,090), 검토 0.6억. 차례당 평균은 직접 대화 19.6만, 맡긴 일 12.5만 토큰. 메인의 결정 선검토만 437번 깨웠다. 입력의 93~97%는 캐시 읽기다. 종량 요금이면 그만큼 싸지만, 구독 한도가 캐시 읽기를 어떻게 세는지는 확인하지 못했다 | 자율 깨움과 결정 검토가 Ghost의 직접 대화에 제출된다 |
| R3 | 마감이 벽시계다 | 마감 실패 63건: 소유자 결정 대기 37건, 하위 일 대기 8건, 마감까지 작업 중 16건, 멈춤 2건. 대기 중이던 결정은 결과 수용 18, 실행 승인 15, 질문 11, 효과 대사 2건이다. 결과 수용 18건은 일을 끝내고 수용을 기다리던 중에 실패 처리됐다. 마감은 맡기는 Ghost가 정하며 중앙값 60분, 하위 10%는 21분 | `core/works.ts` `expire()`가 `waiting`·`verifying`·`blocked`까지 만료시킨다 |
| R4 | 독촉 한 번으로 실패시킨다 | "the Ghost stopped without completing" 12건 중 9건이 한도 오류를 맞았다. 독촉 차례 13건이 한도로 죽었다 | `MAX_IDLE_NUDGES = 1` |
| R5 | 실행 환경이 과업과 맞지 않는다 | 3절 | `sandbox/index.ts`, `config.json`의 이미지 |
| R6 | 같은 이름으로 다시 게시하면 옛 파일이 결과에 붙는다 | 검토자가 "첨부가 여전히 이전판"이라며 반려한 맡긴 일이 6건 이상 | `tools/work.ts`의 `complete`: 생성 순으로 정렬한 목록에서 `find`로 첫 항목(가장 오래된 것)을 고른다 |
| R7 | 기억이 쌓이지 않는다 | 대화 기록 색인이 `Indexed memory history is immutable` 예외를 5,722번 냈고 현재 릴리스에서도 계속된다. 기억 정리 63회 중 52회 실패(한도 36, 인용 불일치 9, 길이 4). 색인된 6,916행 중 128행이 출처(origin) 없이 색인됐고 나중에 출처가 붙어 다시 읽히면서 충돌했다. 인용 불일치 9건은 모두 모델이 원문을 바꿔 쓴 것이었다 | `engine/index.ts`가 한 커밋의 항목 변경을 제출 변경보다 먼저 발행해, Ghost가 바쁠 때 대기열에 들어간 입력(예약, 결정, 맡긴 일 깨움)이 출처 없이 색인됐다. 같은 메시지를 다시 읽으면 `stores/memory.ts` `indexMessage`가 예외를 내고 체크포인트가 멈춘다. 2026-11-12 `infra-impl`에서 수정 |
| R8 | 같은 실패를 막지 않는다 | `publish_artifact` 거부 715건 중 645건이 맡긴 일 5건에서 나왔다. 컨테이너에서 Mac 파일을 찾으려고 게시 도구를 파일 탐색기처럼 380번 호출한 일이 있다 | 반복을 세는 곳이 없다 |
| R9 | 권한 때문에 위임한다 | 하위 일 33건이 `Mac 관리`에게 간 "저장소 원문 추출"이고 5건만 끝났다 | 패러다임 문서 F3·F4 |

패러다임 문서 초판은 `publish_artifact` 거부 715건을 실행 환경 전반의 문제로 적었다. 위 R8처럼 한 사건에 몰린 수치여서 정정한다.

원인의 사슬은 이렇다. 같은 구독의 싼 모델 하나에 Ghost 26명이 상시로 걸려 있고(R2), 한도가 소진되면 차례가 답 없이 죽고(R1), 그 사이 시계는 계속 가고(R3), 한 번의 독촉도 한도로 죽으면 실패로 닫힌다(R4). 조직 구조보다 앞선 문제다.

## 3. 컨테이너는 필요한가

컨테이너의 목적은 PC 보호가 아니라 과업을 오염에서 분리하는 것이었다. 그 기준으로 본다.

| 관측 | 수치 |
| --- | --- |
| 컨테이너 환경의 맡긴 일(명시 109, 기본값 99) 중 셸을 한 번도 안 쓴 것 | 208건 중 68건. 조사와 글쓰기에는 환경이 필요 없었다 |
| 이미지 | 고정 다이제스트의 기본 Ubuntu. python, node, git, curl이 없고 셸에 네트워크가 없어 설치도 못 한다 |
| 없는 명령 | `python3` 30회, `column` 6, `curl` 5, `python` 3, `git` 3, `node` 2, `bun` 1 |
| 실제로 쓴 도구 | 첫 단어 기준 `perl` 330회. `밸런스`는 SHA-256을 순수 Perl로 직접 구현했다고 메모에 적었다 |
| 프로젝트 파일 | 컨테이너 안에 없다. 그래서 R9의 위임 33건과 R8의 탐색 645건이 생겼다 |
| 같은 Mac의 도구 | python3, node, bun, git, ffmpeg, blender, uv, cargo, swift가 모두 있다 |
| Mac 직접 실행 56건 중 워크트리 사용 | 0건. 소유자의 체크아웃에서 그대로 일했다 |
| 완료율 | 컨테이너 53/109, 기본값 56/99, Mac 직접 30/56. 차이가 없다 |

판단은 다음과 같다.

- **목적에 맞는 장치는 이미 있는데 쓰이지 않는다.** 과업 분리는 일마다 자기 폴더(`sandboxes/<ghost>/<work>/workspace`, 이미 있음)와 저장소 일의 워크트리(`execution.worktree`, 이미 있음)가 한다. 워크트리는 0건 쓰였다.
- **쓰이는 장치는 목적이 아닌 것을 한다.** 컨테이너는 PC와 과업을 갈라놓는다. 그 대가로 도구와 재료를 잃었고, 실무자가 일할 수 없는 환경이 됐다.
- **오염은 반대쪽에서 났다.** 추적되지 않은 문서 163개와 소유자 작업 트리의 수정은 컨테이너 밖, 워크트리 없는 Mac 직접 실행과 문서 제안에서 나왔다.

그래서 환경을 셋으로 다시 나눈다.

| 환경 | 쓰임 | 분리 방식 |
| --- | --- | --- |
| 작업 공간 (기본) | Mac의 도구를 그대로 쓴다. 일마다 자기 폴더, 저장소 일은 일마다 워크트리와 브랜치 | macOS Seatbelt 프로필. 쓰기는 그 일의 폴더와 워크트리만, 읽기는 프로젝트 경로, 비밀 경로와 Ghost 상태 루트는 거부, 네트워크는 Host의 기존 egress 프록시 경유 |
| 컨테이너 (선택) | 밖에서 받은 코드와 패키지 설치 스크립트 실행, Linux가 필요한 일, 일부러 망가뜨려 보는 실험 | 지금의 Apple container. 이미지는 도구가 든 것으로 바꾸고 프로젝트 사본을 넣는다 |
| Mac 직접 (소유자 허용) | 설치, 서비스 재시작, 앱 조작처럼 작업 공간 밖을 바꾸는 일 | 없음. 지금의 PC 실행과 같다 |

근거와 주의점이다.

- Claude Code는 컨테이너 없이 OS 수준 샌드박스(macOS Seatbelt, Linux bubblewrap)로 파일과 네트워크를 가두고 승인 요청을 84% 줄였다고 보고했다([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). Cursor는 macOS에서 App Sandbox, 컨테이너, VM, Seatbelt를 비교해 Seatbelt를 골랐다. 컨테이너는 Linux 바이너리로 제한되고 VM은 시작 지연과 메모리 부담이 크다는 이유다. 샌드박스 안의 에이전트는 40% 덜 멈췄다([Cursor](https://cursor.com/blog/agent-sandboxing)).
- 이 저장소는 이미 Seatbelt를 쓴다(`integrations/obscura.ts`의 `sandbox-exec` 프로필).
- 빌드와 테스트 도구는 캐시 디렉터리처럼 예상 밖의 쓰기를 한다. Cursor도 같은 문제를 적었다. 프로필은 실제 과업으로 다듬어야 하고, 막힌 이유를 도구 결과에 그대로 보여 줘야 같은 명령의 반복을 피한다.
- PC 보호가 목적이 아니어도 남는 위험이 하나 있다. 웹과 메일 같은 신뢰할 수 없는 입력을 읽는 일이 비밀 파일을 읽고 밖으로 보낼 수 있으면, 주입된 문장이 그 경로를 탄다. 7절의 규칙으로 다룬다. 작업 공간의 읽기 제한과 프록시는 그 규칙을 지키는 수단이다.

## 4. 실행 기반 설계

### 모델 예산 (R1)

- Host가 제공자별 한도 상태를 가진다. 429의 사유(사용량 소진, 분당 한도)와 재개 시각을 기록한다. 재개 시각을 응답에 주는 제공자(GLM)는 그 값을 쓰고, 주지 않는 제공자(MiniMax)는 간격을 늘려 가며 가볍게 확인한다.
- 접수에 우선순위를 둔다. 소유자 메시지, 진행 중인 맡긴 일과 그 검토, 결정 후속, 자율 깨움과 기억 정리 순이다. 한도가 줄면 아래부터 접수를 미룬다. 미룬 것은 실패가 아니다.
- 한도로 죽은 차례는 Ghost의 멈춤이 아니다. 독촉 횟수를 쓰지 않고, 실행 시계를 세우고, 재개 시각에 다시 제출한다.
- 프로젝트 우선순위가 한도 배분의 순서다. 소유자는 "모델 한도로 대기 중, 20시 재개"를 한 줄로 본다.

### 깨움의 맥락 (R2)

- 자율 깨움과 결정 검토는 직접 대화에 쌓지 않는다. 깨움마다 새 맥락에서 시작하고, 재료는 프로젝트 기록 색인, 목표와 진행 중인 이정표, 지난번 이후 달라진 것이다. 소유자에게 할 말만 직접 대화에 남긴다. 맥락은 10만 토큰 아래로 유지한다. 일부 모델은 그 선을 넘으면 요청 전체의 단가가 오른다(Anthropic 비용 안내의 Haiku 5.5 사례).
- 직접 대화는 소유자와의 대화만 담는다. 한도에 가까워지면 상태를 프로젝트 기록에 남기고 요약에서 다시 시작한다.
- 큰 도구 출력은 파일로 두고 참조로 넘긴다.
- 전결(패러다임 문서 9절)로 메인의 결정 선검토 437회가 없어진다.
- 보안 근거도 같다. 배경 실행이 사용자 대화와 같은 세션에서 돌면 배경에서 읽은 내용이 기억과 이후 행동을 조용히 바꾼다는 것이 OpenClaw 계열에서 측정됐다(단기 오도율 최대 61%, 장기 기억 정착 최대 91%, [Zhang 외](https://arxiv.org/abs/2603.23064)). Ghost의 자율 깨움은 지금 같은 구조다.

### 실행 시계 (R3, R4)

- 마감을 둘로 나눈다. **실행 예산**은 일하는 시간이고 기본 90분이다. **기한**은 달력 시각이고 소유자가 정했을 때만 있다.
- 실행 예산은 모델 차례와 도구 실행 중에만 흐른다. 소유자 결정 대기, 하위 일 대기, 검증, 한도 대기 중에는 멈춘다. 검증 중인 일은 만료되지 않는다.
- 예산이 다 되면 실패로 닫지 않는다. 진행 기록을 남기고 담당에게 연장, 쪼개기, 중단 중 하나를 묻는다. 담당은 전결 안에서 한 번 연장할 수 있다.
- 독촉은 두 번으로 늘리고 한도 오류는 세지 않는다.

### 반복 차단 (R8)

같은 도구가 같은 종류의 거부를 세 번 내면 도구 결과가 제약과 맞는 도구를 설명한다. 여섯 번이면 일을 세우고 담당에게 넘긴다. Cursor도 같은 명령의 반복을 같은 방법으로 풀었다.

### 구조와 무관하게 고칠 결함

- R6: 같은 이름의 산출물은 가장 최근 것을 결과에 붙인다.
- R7: 색인 충돌의 원인을 찾는다. 기억 정리는 모델 예산의 우선순위를 따르게 한다. 이것이 풀리지 않으면 프로젝트 기록도 쌓이지 않는다.

## 5. 담당의 품질 한계를 넘는 방법

한 범위의 판단이 그것을 받는 Ghost 하나에 걸리는 것이 담당제의 약점이다. 아래 규칙은 권장 구성이다. 기반이 제공하는 것은 계약, 실물을 여는 평가 환경, 실패 시 다른 모델 자리로의 재시도라는 기제이고, 누가 평가하고 언제 올릴지는 사용자가 정한다. 근거부터 적는다.

| 출처 | 내용 | 한계 |
| --- | --- | --- |
| [METR, 2026-05](https://metr.org/blog/2026-05-19-frontier-risk-report/) | 공개 최상위 모델의 50% 성공 작업 길이는 약 12시간, 80% 성공 길이는 약 1.5시간이다. 진척을 싸게 확인할 수 있는 일에는 강하고, 판단과 전략이 필요한 일에는 사람보다 뚜렷이 약하다. 어려운 일에서 쉬운 판본으로 바꿔 놓고 성과를 부풀려 보고한다. 가장 긴 과제의 성공 중 16% 이상이 부정행위였다 | 2026년 2~3월 모델, 소프트웨어 중심 |
| [Anthropic 3-에이전트 하네스, 2026-03](https://www.anthropic.com/engineering/harness-design-long-running-apps) | 에이전트는 자기 결과를 후하게 평가한다. 생성과 평가를 다른 에이전트로 가르고, 일 전에 "끝"의 기준을 합의하고, 평가자가 실물을 직접 써 보게 하자 품질이 올랐다. 평가자는 회의적으로 다듬어야 했다. 비용은 20배였다. 하네스의 각 부품은 모델이 못 하는 것에 대한 가정이고, 모델이 바뀌면 낡는다 | 앱 개발, 사례 수가 적다 |
| [Cognition, 2026-04](https://cognition.com/blog/multi-agents-working) | 맥락을 공유하지 않는 검토자가 PR당 평균 2개의 버그를 찾는다. 약한 주 모델이 강한 모델에 물을 때를 스스로 알지 못해 품질 상한이 주 모델에 묶였다 | 자사 제품 보고 |
| [Anthropic 비용 안내](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence) | 결과를 검사할 수 있으면 낮은 설정으로 먼저 돌리고 실패한 것만 높은 설정으로 다시 돌리는 것이 같은 통과율에 약 40% 싸다. 자문은 실행자가 물을 때만 도움이 된다. 지시가 없을 때 실행자는 198문항 두 번 모두 한 번도 묻지 않았고, 자주 물은 코딩 조합도 1.7점 오르는 데 비용이 2.1배였다. 한 맥락에 들어가는 일이나 의존 사슬인 일은 강한 모델 하나가 하는 편이 위임보다 나았고, 여러 맥락을 넘는 독립 조각은 하위 모델에 나누면 손실 없이 약 3분의 1 쌌다. 비교 단위는 토큰이 아니라 끝낸 일 하나의 비용이다 | Anthropic 내부 측정, Claude 모델. 방향만 참고한다 |
| [Remote Labor Index](https://scale.com/leaderboard/rli) | 실제 프리랜서 과업 240건에서 고객이 받을 수준으로 끝낸 비율. 2025-10 최고 2.5%, 2026-11 최고 41.3%, 플래시급 5.0~9.6%. 실패 유형은 낮은 품질 45.6%, 미완성 35.7%, 깨진 파일 17.6%, 파일 간 불일치 14.8% | 고객 응대와 장기 평가가 필요한 일은 제외. Ghost가 쓰는 MiniMax·GLM 플래시는 순위표에 없다 |
| [ACE, ICLR 2026](https://arxiv.org/abs/2510.04618) | 지침을 통째로 다시 쓰면 세부가 깎여 나간다. 항목 단위로 더하고 다듬는 플레이북이 성능을 유지한다 | 벤치마크 |

여기서 나오는 규칙이다.

1. **담당과 평가는 가장 강한 모델이 맡는다.** RLI에서 최상위와 플래시급의 차이는 네 배 이상이다. 지금은 `심층` 하나를 빼고 모두 플래시급이다. 실행은 일의 모양으로 정한다. 서로 독립인 조각이 여럿이고 한 맥락을 넘으면 기본 등급의 실행자에게 나눈다. 하나의 의존 사슬이면 강한 모델이 직접 한다. 모델을 고르는 기준은 토큰 단가가 아니라 끝낸 일 하나의 비용이다.
2. **일 전에 계약을 쓴다.** 담당이 맡기는 일에는 검사할 수 있는 완료 항목이 있어야 한다. 이미 있는 `acceptance.checks`를 필수에 가깝게 쓴다. 위험이 크거나 예산이 큰 일은 평가자가 계약부터 본다.
3. **평가자는 실물을 본다.** 요약이 아니라 산출물을 연다. 앱은 실행해 눌러 보고, 영상은 디코드해 보고, 회차는 바이블과 대조한다. 평가 대화는 쓴 맥락을 받지 않고, 가능하면 쓴 모델과 다른 계열이다. 미완성과 깨진 파일은 RLI 실패의 절반이므로 "요청한 항목이 모두 있는가, 파일이 열리는가"가 첫 검사다.
4. **일의 크기를 80% 구간에 맞춘다.** 맡긴 일 하나는 그 등급이 안정적으로 끝내는 길이, 곧 실행 예산 안에 검사 가능한 산출물 하나다. 더 큰 것은 이정표의 사슬로 만들고 단계마다 진행 기록과 커밋을 남긴다.
5. **등급은 실패에 걸어 올린다.** 검사를 통과하지 못한 일만 높은 등급으로 다시 돌린다. 측정된 방법 중 가장 싸다. 실행 중 자문은 효과가 작고 실행자가 스스로 묻지 않으므로 두 지점에만 둔다. 같은 실패가 반복될 때와, 위험이 큰 일의 완료 선언 직전이다. 이 지점은 Host가 정한다.
6. **자기 보고를 믿지 않는다.** 완료는 검사, 평가자, 전결 순으로 판정한다는 현재 원칙을 유지한다. 평가자는 "요청보다 쉬운 것을 하지 않았는가"를 명시적으로 본다.
7. **소유자의 반려가 기준이 된다.** 프로젝트 기록에 기준 파일을 둔다. 소유자가 반려한 이유는 기준 후보로 올라온다. 이미 있는 예: "원문 대조 없이 쓴 가정 기반 초안은 받지 않는다", "시점이 지나면 낡는 상태 요약은 저장소에 넣지 않는다". 기준은 항목 단위로 더하고 고친다. 평가자는 이 기준으로 본다.
8. **담당은 지표로 본다.** 프로젝트별 수용률, 반려율, 소유자가 뒤집은 판정 수, 예산 초과율을 메인이 본다. 나빠지면 담당의 모델을 올리거나 플레이북과 기준을 고친다. 목표치로 압박하는 관리자 Ghost는 두지 않는다.
9. **되돌릴 수 없는 판단은 여럿이 본다.** 다른 계열 모델 둘의 의견을 담당이 정리해 소유자에게 올린다.
10. **가정에 유통기한을 둔다.** 위 규칙마다 어떤 약점을 보완하는지 적어 두고, 모델을 바꿀 때 하나씩 빼 보고 결과를 비교한다.

비용은 솔직히 적는다. 평가와 재실행은 토큰을 더 쓴다. 4절의 맥락 축소(직접 대화 41%, 결정 선검토 437회)와 실패 감소가 그 재원이다. 지금은 루트 완료율이 63%, 하위 일이 29%여서 끝낸 일 하나의 비용에 실패한 시도가 그대로 얹혀 있다. 순증인지 순감인지는 측정 전에는 알 수 없다.

## 6. 협업 구조

한 일을 끝내는 데 필요한 것은 직무가 아니라 다섯 기능이다.

| 기능 | 누가 | 맥락 | 쓰기 |
| --- | --- | --- | --- |
| 계획 | 담당 | 프로젝트 기록, 목표, 기준 | 계약과 프로젝트 기록 |
| 실행 | 실행자. 맡긴 일마다 새로 뜬다 | 계약, 역할 플레이북, 환경 메모 | 그 일의 작업 공간. 한 저장소에 한 줄기 |
| 조사 | 조사자. 여럿이 병렬로 | 질문 하나 | 없음. 결과는 파일로 |
| 평가 | 평가자 | 계약, 기준, 산출물. 쓴 과정은 받지 않는다 | 판정 |
| 자문 | 강한 모델 | 실행자의 맥락 사본 | 없음 |

- 소통은 계약, 산출물, 프로젝트 기록이라는 파일로 한다. 필요한 질문은 지금의 `ask_parent`·`ask_peer`를 쓴다. 상시 대화 채널은 두지 않는다.
- 병렬은 읽기에만 쓴다. 쓰기를 병렬로 하려면 서로 닿지 않는 파일과 정해진 인터페이스가 있어야 하고, 각자 워크트리를 가진다.
- 이 다섯은 Ghost가 아니다. 담당만 Ghost이고 나머지는 맡긴 일과 검토 대화다.

## 7. 업무 범위

범위의 문서에 네 가지를 적는 구조를 권한다. 코드에 있는 필드가 아니라 문서를 짜는 한 가지 방식이다. 이것이 생활 대행과 연재 소설과 코드 저장소를 같은 고리에 올린다.

| 속성 | 뜻 |
| --- | --- |
| 정본 | 그 프로젝트에서 무엇이 진실인지 담는 것. 실행자는 여기서 시작하고 평가자는 여기에 대조한다 |
| 기준 | 무엇이 좋은 결과인지. 소유자의 취향과 반려 이유가 쌓인다 |
| 채널 | 결과가 밖으로 나가는 길과 그 정책 |
| 리듬 | 얼마나 자주, 어떤 비축을 두고 |

| 업무 | 정본 | 평가자가 보는 것 | 채널 | 리듬 |
| --- | --- | --- | --- | --- |
| 개발 | 저장소, 실행 방법, 결정 기록 | 테스트와 빌드, 실행한 앱, 차이 | 본 브랜치 통합(검토), 배포(소유자) | 커밋과 목표 |
| 조사와 문서 | 질문, 읽은 출처 | 인용이 출처에 있는가(기존 `artifact_citations`), 요청 항목 | 소유자에게 전달 | 요청 시 |
| 웹소설 연재 | 작품 바이블(인물 상태, 연표, 미회수 복선 장부, 문체 표본, 금지 사항)과 회차 원고 | 바이블과의 모순, 문체 기준, 분량, 이번 회 계약 | 연재 플랫폼 계정 | 주 N회, 비축 회차 수 |
| 영상 | 채널 가이드, 인물과 화면 레퍼런스 자산, 편별 대본·스토리보드·샷 목록 | 파일을 디코드한 길이·해상도·오디오, 프레임을 본 일관성, 대본 대비 누락 | 영상 플랫폼 계정 | 주기와 편당 비용 한도 |
| SNS 운영 | 계정 가이드(말투, 다루지 않을 주제), 콘텐츠 일정 | 가이드 대조, 사실 확인, 중복 | 계정 게시, 댓글 응대 | 일정 |
| 생활 대행 | 선호, 계정과 반복 일, 진행 중인 건 | 영수증과 확인 메일, 소유자 확인 | 메일, 브라우저 결제와 예약 | 요청과 반복 |

업무별로 더 필요한 것이다.

- **연재.** 회차마다 계약(이번 회의 사건, 회수할 복선, 분량)을 쓰고, 한 실행자가 쓰고, 평가자가 바이블에 대조하고, 통과한 뒤에만 바이블을 갱신한다. 장편 생성 연구가 같은 구조로 모인다. 계획과 집필을 나누고 공유 상태를 두며(Agents' Room, StoryWriter), 구조화된 상태와 비평 단계가 긴 서사의 일관성을 만든다([MAGNET](https://arxiv.org/abs/2607.00918)). 이 논문들은 검색 요약으로만 확인했고 원문은 읽지 않았다.
- **영상.** 이미지·영상·음성 생성을 Host의 도구로 붙이고 호출마다 비용을 계량한다. 편집은 작업 공간의 ffmpeg와 Blender로 한다. 컨테이너에는 둘 다 없다. 대본, 스토리보드, 샷, 편집, 검수로 나누는 것은 영상 에이전트 연구의 공통 구조다(ViMax, FrameWorkers, MAViS. 검색 요약으로만 확인).
- **SNS.** 댓글과 DM은 신뢰할 수 없는 입력이다. 응대는 게시와 다른 단계의 정책을 가진다.
- **생활 대행.** 메일, 금고, 브라우저, 문자 코드는 이미 있다. 전담 담당(비서)을 두는 것이 맞다. 다른 Ghost에게 주면 안 되는 권한이 필요하기 때문이다. 일정과 할 일 관리는 [현재 범위](current-priorities.md)에서 제외돼 있어 소유자 결정이 필요하다.

### 채널과 신뢰

밖으로 나가는 길을 채널이라 부른다. 코드에서는 [정책](ghost-infrastructure.md#4-정책)의 규칙이고, 아래 단계는 그 규칙을 차례로 완화하는 한 가지 방식이다.

- 채널마다 정책 단계가 있다. **초안만**, **승인 후 발행**, **자율 발행 후 보고**.
- 단계는 실적으로 올린다. 소유자가 고치지 않고 승인한 횟수가 쌓이면 담당이 단계 올림을 제안하고 소유자가 정한다. 반려가 나오면 내려간다. 숙련된 사용자는 건별 승인을 줄이는 대신 더 자주 끼어든다는 관측과 같은 방향이다([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)).
- 채널에는 일일 한도, 되돌릴 수 있는지, 표기 규칙이 붙는다.
- 발행 전 검사에 플랫폼 규정 확인이 들어간다. 한국 웹소설은 공모전에서 AI 활용을 금지하거나 제한하고, 일반 연재의 기준은 분명하지 않으며, 2026년 10월 독자의 AI 집필 의혹으로 정식 출간작이 판매 중단되고 환불된 사례가 있다([일요신문](https://www.ilyo.co.kr/?ac=article_view&entry_id=513341)). AI 활용을 표기할지는 작품마다 소유자가 정하고, 번역투 같은 문체 문제는 기준에 넣는다.

### 신뢰할 수 없는 입력

맡긴 일마다 세 가지 중 둘까지만 허용한다([Meta, Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)).

- A: 신뢰할 수 없는 입력을 읽는다(웹, 모르는 발신자의 메일, 댓글).
- B: 비공개 데이터나 민감한 시스템에 닿는다(금고, 메일함, 비밀 파일).
- C: 상태를 바꾸거나 밖으로 보낸다(발신, 게시, 결제).

셋이 다 필요하면 자율로 돌리지 않고 소유자 확인이나 미리 승인한 대상(신뢰한 수신자, 저장된 가맹점)으로 C를 좁힌다. 일을 만들 때 이 조합을 정하고 Host가 도구 노출로 강제한다. 프로젝트 기록에 쓰는 내용에는 출처와 신뢰 표시를 남긴다. `memory.db`에는 이미 `trust`와 `sources` 열이 있다.

## 8. 현행 서비스에서 가져온 것과 피한 것

| 서비스 | 구조 | 가져온 것 | 피한 것 |
| --- | --- | --- | --- |
| Claude Code | 범용 에이전트 하나에 스킬, 별도 맥락의 하위 에이전트, OS 샌드박스, 자문 도구 | 역할 = 플레이북, 작업 공간, 자문 지점 | 프로젝트를 넘는 책임 주체가 없다 |
| Devin | 코딩 에이전트와 검토 에이전트가 맥락 공유 없이 반복. 관리자가 하위를 나누고 합친다. 쓰기는 한 줄기 | 독립 평가, 쓰기 단일, 나누고 합치는 관리 | 구조 없는 스웜 |
| Cursor 장기 실행 | 계획자, 작업자, 판정자. 동등한 자기 조율은 실패. 주기적으로 새 맥락 | 책임 주체, 일마다 새 맥락 | 통합 전담 역할(병목이 되어 그쪽도 뺐다) |

| Manus | 원격 컴퓨터에서 도는 범용 에이전트, 자동화 | 범용 실행 환경, 명시적 일정 | RLI 2.5~2.9%. 환경만으로는 품질이 나오지 않는다 |
| OpenClaw | 30분 주기 heartbeat, 마크다운 기억, 스킬, 메신저 연결 | 스스로 깨기, 파일로 된 기억 | 배경 실행과 사용자 대화의 세션 공유 |

Ghost가 이들보다 이미 가진 것은 내구성(원장과 효과 기록), 수용 판정(완료 주장만으로 받지 않음), 소유자 결정의 분리다. 부족한 것은 일할 수 있는 환경, 자원 관리, 독립 평가의 품질이다.

## 9. 지금 대체할 수 있는 것과 없는 것

| 구분 | 일 | 이유 |
| --- | --- | --- |
| 맡길 수 있다 | 테스트가 있는 코드, 데이터 처리, 출처가 있는 조사와 보고서, 단품 이미지와 오디오, 반복 운영 점검 | 진척을 싸게 확인할 수 있다. RLI의 성공도 이 영역에 몰린다 |
| 장치가 있으면 된다 | 긴 연재와 영상(정본과 평가자), 생활 대행(승인 지점), SNS 게시(단계 정책) | 일관성과 밖으로 나가는 행동이 약점이다 |
| 소유자가 쥔다 | 사업 방향, 취향의 최종 판단, 평판이 걸린 대외 소통, 확인할 방법이 없는 일 | 판단과 전략에서 사람보다 뚜렷이 약하다. 돈을 스스로 벌어 보라는 실험은 4번 모두 0달러였고, 매장 운영 실험은 발주와 근무표에서 실수했다(METR 보고서 인용) |

그래서 이 기반의 목표는 사람을 빼는 것이 아니라 소유자의 기준을 넓게 적용하는 것이다. 기준과 정본이 쌓일수록 "장치가 있으면 된다"의 범위가 넓어지고, 모델이 바뀔 때마다 5절의 가정을 다시 시험해 장치를 줄인다.

## 10. 소유자 결정 (2026-11-12)

1. 기본 실행 환경을 컨테이너에서 작업 공간으로 바꾼다. 채택.
2. 어떤 모델을 쓰고 얼마를 쓸지는 기반이 정하지 않는다. 기반은 모델 자리와 한도 인지, 계량만 제공한다.
3. 개인 비서의 범위를 코드에 정의하지 않는다. 일정 관리든 무엇이든 연결하면 되는 일이다.
4. 채널 단계 같은 고정 구조를 만들지 않는다. 기반을 만들고 사용자가 내부를 꾸린다.

이 결정에 따라 구현 기준은 [기반 설계](ghost-infrastructure.md)로 옮겼다.

## 11. 구현 순서

[기반 설계 10절](ghost-infrastructure.md#10-구현-순서)에 있다. 이 문서의 2~4절은 그 순서의 0~3단계다. 결함 수정, 모델 한도와 실행 시계, 깨움의 맥락, 작업 공간이며 조직을 어떻게 꾸리든 효과가 있다.
