# Ghost 제품 개념

상태: **정본, Ghost 3.0** (2026-11-28 소유자 지시). 제품이 무엇인지와 메인·Ghost·패키지·프로젝트·맡긴 일이 각각 무엇을 맡는지 정한다. 구조는 [architecture](architecture.md), 범위와 순서는 [current-priorities](current-priorities.md)를 따른다. 2026-11-25판의 「일하는 방식마다 Ghost」를 이어받고, Ghost를 앱처럼 **설치**하는 단위와 메인 아래의 **위계**를 더했다.

## 1. 한 문장

**메인 Ghost가 입구이고, 다른 Ghost는 하는 일에 맞춰 앱처럼 설치해 쓰는 AI 동료다.** 앱을 깔 듯 「개발」「소설」 Ghost를 설치하면, 그 Ghost는 정해진 모델·도구·말투로 자기 프로젝트를 맡는다. 무엇을 하려는지 모르겠거나 여러 갈래에 걸친 일은 메인에게 말한다.

## 2. 다섯 가지

| | 답하는 질문 | 담는 것 | 예 |
| --- | --- | --- | --- |
| **메인** | 어디에 말하나 | 소유자의 입구, 다른 Ghost의 설치·설정, 일의 연결 | 하나뿐이다 |
| **Ghost** | 누구와, 어떻게 | 페르소나(말투·일의 기준), 모델, 도구와 권한, 스킬, 기억 | 개발, 소설 |
| **패키지** | 무엇을 설치하나 | Ghost 하나를 이루는 페르소나·모습·도구·스킬·PC 실행 요청·권장 모델·받을 프로젝트 종류 | `dev`, `writer` |
| **프로젝트** | 무엇을 | 폴더, 문서 금고, 함께 읽을 자료, 목표, 자동 활동, 승인 규칙 | 연재 작품 하나, 저장소 하나 |
| **맡긴 일** | 이번에 무엇을 끝내나 | 완료 기준, 새 맥락, 실행 증거 | 3화 초고, 로그인 버그 수정 |

대화 하나의 맥락은 이 순서로 쌓인다. Ghost의 페르소나, 대화 종류의 지시, Ghost의 기억과 환경 적응, 프로젝트의 자료, 맡긴 일. 앞의 것은 그 Ghost의 모든 일에, 뒤의 것은 그 프로젝트나 그 일에만 들어간다.

## 3. 왜 Ghost가 앱인가

소설 Ghost와 개발 Ghost는 맥락만 다른 게 아니다.

| 다른 것 | 소설 | 코딩 |
| --- | --- | --- |
| 모델 | 문장이 좋은 모델 | 코드와 도구 사용이 좋은 모델 |
| 도구와 권한 | 문서, 웹 조사. Mac을 바꿀 일이 없다 | `code_run`, 저장소 읽기, 필요하면 PC 실행 |
| 일의 기준 | 소유자의 문체를 지킨다, 장면 단위로 고친다 | 테스트와 실행 출력으로 증명한다 |
| 말투 | 편집자처럼 취향을 말한다 | 짧게, 근거와 위험만 |

프로젝트 맥락은 **무엇**을 바꾸고 Ghost는 **어떻게**를 바꾼다. 작품의 설정집이나 저장소 규칙을 넣는다고 모델과 권한과 말투가 바뀌지는 않는다. 그래서 프로젝트 맥락만으로는 두 일을 한 Ghost에 담을 수 없다.

반대로 방식이 같으면 Ghost를 나누지 않는다. 소설 두 편은 소설 Ghost 하나에 프로젝트 둘이다. 같은 Ghost라서 취향과 기억이 이어지고, 작품마다 다른 설정집은 각 프로젝트에 있어서 섞이지 않는다.

2.x에서는 이 차이를 소유자가 빈 페르소나 칸에 직접 써야 했다. 그래서 실제 설치에는 메인 하나만 남았고 따로 Ghost를 만들 이유가 보이지 않았다(2026-11-28 운영 상태: 활성 Ghost는 메인 하나, 프로젝트 13개 모두 메인이 받음). 3.0은 그 차이를 **패키지**에 미리 담아, 설치하는 순간 무엇이 달라지는지 보이게 한다.

## 4. 메인과 설치한 Ghost

위계는 둘뿐이다. 메인과 그 아래의 Ghost다. Ghost 아래에 Ghost는 없다.

| | 메인 | 설치한 Ghost |
| --- | --- | --- |
| 수 | 하나, 바꿀 수 없다 | 하는 일마다 하나 |
| 받는 일 | 어느 Ghost의 일인지 모르는 일, 프로젝트가 없는 일, 받을 Ghost가 없는 프로젝트 | 자기 프로젝트와 자기에게 맡긴 일 |
| 위임 | 어느 Ghost에게나 | 자기 자신(새 맥락)과 메인에게만. 다른 방식의 일이 필요하면 메인에게 넘기고 메인이 고른다 |
| 설정 도구 | 프로젝트·승인 규칙·모델 조합·한도·외부 도구 서버·되돌리기, Ghost 설치와 설정 | 기본으로 없다. 필요하면 `capability_request`로 요청 |
| 상태 | 늘 사용 중 | 사용·일시정지, 제거 |

메인은 소유자가 지정을 바꾸는 역할이 아니다. 2.x의 「메인으로 지정」은 없앴다. 설치한 Ghost끼리 직접 의뢰하던 2026-11-10 결정도 바꿨다. 앱끼리 서로를 부르지 않고 운영체제를 거치듯, 다른 방식의 일은 메인을 거친다. 같은 과업 안의 질문(`ask_parent`·`ask_peer`)은 그대로다. 책임이 아니라 사실을 묻는 연결이기 때문이다.

메인은 직접 대화에서 Ghost를 설치하고 고친다. 소유자가 방식이 다른 일을 시작하면 메인이 맞는 패키지를 제안하고, 소유자가 승인하면 설치한 뒤 그 방식의 프로젝트를 넘긴다. 맞는 패키지가 없을 때만 페르소나를 직접 써서 만든다.

## 5. 패키지

패키지는 스킬처럼 하나로 묶인 일하는 방식이다. 스킬이 한 절차를 묶는다면 패키지는 Ghost 하나를 묶는다.

- **들어 있는 것**: 이름, 버전, 페르소나, 모습(몸 색·모양·눈·장식이 앱 아이콘이 된다), 도구 목록, 스킬, PC 직접 실행 요청, 권장 모델(말로 적은 것), 받을 프로젝트 종류(`code`·`documents`·없음).
- **들어 있지 않은 것**: 모델 id. 모델은 설치할 때 소유자가 고르고 권장 문구가 옆에 보인다. 등록된 제공자는 설치마다 다르기 때문이다.
- **출처**: Host에 들어 있는 내장 패키지와, 상태 루트의 `ghost-packages/<이름>/GHOST.md`에 둔 소유자 패키지. `GHOST.md`는 YAML 앞머리(`name`·`title`·`version`·`tools`·`skills`·`hostExecution`·`modelHint`·`projects`·`look`)와 페르소나 본문이다. 스킬 폴더처럼 파일을 두면 「Ghost 추가」에 나타난다.
- **내장 패키지**(2026-11-28): 개발, 소설, 리서치, 마케팅(X·SNS 게시), 3D 모델링, Mac 관리, 자산. 게임 개발은 따로 두지 않는다. 모델과 도구가 개발과 같으므로 개발 Ghost에 `game-dev-workflow` 스킬을 붙인다.
- **설치**: 패키지 하나는 한 번만 설치된다. 설치한 Ghost는 출처(`source`: 패키지 이름과 버전)를 기억한다. 이 Host에 없는 스킬은 빼고 설치한다. PC 직접 실행을 요청하는 패키지는 설치 화면에서 허용 여부를 고른다.
- **고침과 되돌리기**: 설치한 Ghost도 페르소나·도구·스킬·모습을 마음대로 고친다. 패키지에서 달라지면 설정에 「패키지대로 되돌리기」가, 패키지의 새 버전이 있으면 「업데이트」가 나타난다. 둘 다 페르소나·모습·도구·스킬만 바꾸고 모델·PC 실행 허용·환경 적응·기억은 그대로 둔다.
- **직접 만들기**: 이름과 페르소나로 출처 없는 Ghost를 만든다. 설치한 Ghost와 같은 기본 도구(시스템 설정 도구를 뺀 것)로 시작한다.

## 6. 프로젝트와의 궁합

프로젝트는 앱에서 여는 문서처럼 Ghost 하나에 속한다.

- 사이드바는 메인과 그 프로젝트가 먼저 오고, 그 아래 「Ghost」 묶음에 설치한 Ghost와 각자의 프로젝트가 온다. Ghost를 누르면 그 Ghost와의 대화가, 프로젝트를 누르면 그 Ghost가 그 프로젝트를 붙여 일하는 방이 열린다([프로젝트 설계](project-design.md)).
- **설치할 때 프로젝트를 옮겨 온다.** 설치 화면은 메인이 받는 프로젝트를 보여 주고, 패키지가 받을 종류에 맞는 것(개발은 git 저장소, 소설은 저장소가 아닌 문서 금고)을 미리 고른다. 설치하면 고른 프로젝트의 받을 Ghost가 새 Ghost로 바뀐다. 설치가 「무엇이 달라지는가」를 보여 주는 자리다.
- **제거하면 프로젝트는 메인으로 돌아온다.** 지난 맡긴 일과 대화의 기록은 남는다.
- 새 프로젝트는 그 프로젝트를 받을 Ghost의 행에서 시작한다.
- 프로젝트는 여전히 권한을 주지 않는다. 받을 Ghost가 없으면 메인이 받는다.

## 7. 새 Ghost를 설치하는 기준

아래 셋 중 하나라도 **그 Ghost의 모든 일에서** 달라야 하면 새 Ghost를 설치하거나 만든다.

1. **모델.** 문장력이 필요한 일과 코드를 고치는 일.
2. **도구와 권한.** PC 직접 실행, 메일 발신, 특정 연결 계정처럼 다른 Ghost에게 주고 싶지 않은 것.
3. **페르소나.** 말투와 좋은 결과의 기준이 다른 Ghost와 부딪친다.

어느 것도 아니면 이미 그렇게 일하는 Ghost에 프로젝트를 더하거나, 맡긴 일에 플레이북(스킬)을 붙인다. 하나의 예외는 기억과 대화가 섞이면 안 되는 일이다(개인 재무와 회사 일). 이때는 방식이 같아도 나눈다.

같은 방식 안의 직무로 Ghost를 가르지 않는다. 기획, 밸런스, 검토자는 플레이북이다. 2026-11-12까지 운영한 역할 Ghost 26명이 이 경우였다. 거의 모두 같은 모델과 도구를 쓰고 300자 안팎의 페르소나만 달랐으며, 위임은 역할이 아니라 권한과 모델을 따라 흘렀다([패러다임](ghost-paradigm.md) F2·F3).

## 8. 페르소나

페르소나는 **이 Ghost가 누구이고 어떻게 일하는가**다. 모든 대화의 맨 앞에 들어간다.

- 첫 줄은 한 줄 소개다. 목록, 검색, 「Ghost 추가」, 위임할 상대를 고르는 화면이 이 줄만 보여 준다.
- 이어서 쓴다: 말투, 이 Ghost에게 좋은 결과란 무엇인가, 혼자 정하는 것과 소유자에게 묻는 것, 하지 않는 것.
- 쓰지 않는다: 작품 하나나 저장소 하나에 관한 사실(그 프로젝트의 자료), 이 Mac에서 통하는 방법(환경 적응), 한 번 쓰는 역할 절차(스킬), 다른 Ghost의 이름(팀이 바뀌면 낡는다).

내장 패키지의 페르소나가 예시다(`apps/ghost-host/src/packages/builtin.ts`).

2026-11-19에는 이 필드를 「책임과 원칙」이라 부르고 캐릭터가 아니라고 좁혔다. 그 근거는 사실 질문 2,410개에서 "당신은 X 전문가" 같은 페르소나 문장이 정확도를 올리지 못했다는 측정이었다([Zheng 외, 2024](https://arxiv.org/abs/2311.10054)). 말투와 결과물의 기준은 그 측정 밖이고, 글쓰기에서는 그것이 곧 결과물이다. 필드 이름(`persona`)과 저장 형식은 바꾸지 않는다.

## 9. 바뀌지 않는 것

- 모든 Ghost는 같은 종류의 지속형 봇이다. 권한은 대화 종류, Ghost의 도구, 연동 허용의 교집합이고 프로젝트는 권한을 주지 않는다.
- 맡긴 일의 계약, 검증, 실행 증거, 바깥 루프 방향(2026-11-21).
- Ghost의 `persona`·`model`·`tools`·`skills`·`attachments`·`hostExecution`과 Scope의 `ghostId`. 3.0은 `source` 하나만 더했다.

## 10. 앞선 결정에서 바뀌는 것

| 앞선 결정 | 3.0 |
| --- | --- |
| 새 Ghost는 이름과 빈 페르소나 칸에서 시작한다 | 패키지에서 설치한다. 직접 만들기는 맞는 패키지가 없을 때 |
| 팀원끼리 메인을 거치지 않고 일을 의뢰한다(2026-11-10) | 설치한 Ghost는 자기 자신과 메인에게만 위임한다. 같은 과업 안의 질문은 그대로 |
| 소유자가 메인을 다른 Ghost로 바꿀 수 있다 | 메인은 하나로 고정된다 |
| 새 Ghost의 기본 도구에 프로젝트·규칙·모델 조합 같은 설정 도구가 들어 있다 | 설정 도구는 메인의 것이고 설치한 Ghost의 기본에서 빠진다 |
| Ghost 상태는 활성·일시정지·은퇴, 삭제는 은퇴한 뒤에 | 사용·일시정지와 제거. 제거하면 프로젝트는 메인으로 돌아온다 |
| 받을 Ghost가 사라진 프로젝트는 사이드바의 「프로젝트」 묶음에 남는다 | 메인 아래에 놓인다 |
| 사이드바 Ghost 목록의 고정·접기·검색 | 없앴다. Ghost는 하는 일마다 하나라 목록이 짧다 |

## 11. 남은 한계

- 한 Ghost의 지속 대화는 하나다. 프로젝트 자료는 메시지마다 그 프로젝트 것으로 바뀌지만, 같은 Ghost가 받는 다른 프로젝트의 앞선 대화도 대화 기록으로 맥락과 화면에 남는다([프로젝트 설계 4절](project-design.md#4-대화의-범위)). 섞이면 안 되는 일이면 방식이 같아도 Ghost를 나눌 수 있다.
- 패키지에는 모델이 없다. 권장 문구를 보고 소유자가 고르며, 고르지 않으면 기본 모델을 따른다.
- 패키지를 다른 사람과 주고받는 저장소는 없다. `GHOST.md` 파일을 옮기는 것이 공유다.
- 근거는 소유자가 실제로 하는 일(코딩, 소설, X 게시, 3D 에셋)과 이 설치의 관측이다. 방식별 Ghost가 단일 Ghost보다 낫다는 비교 측정은 없다.
