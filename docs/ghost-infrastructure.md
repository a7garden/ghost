# Ghost 기반 설계: 코드가 보장하는 것과 사용자가 꾸리는 것

상태: **채택한 설계 기준** (2026-11-12 작성). 아래의 「지금」과 구현 순서는 설계 당시의 기록이다. 현재 코드의 동작은 [architecture](architecture.md)를 따른다. 운영 데이터의 마이그레이션 승인은 10절의 별도 절차를 따른다.

2026-11-12 소유자 결정을 반영했다.

- 기본 실행 환경은 컨테이너가 아니라 Mac의 작업 공간이다.
- 어떤 모델을 쓰고 얼마를 쓸지는 기반이 정할 일이 아니다.
- 일정 관리든 무엇이든 업무 영역을 코드에 정의하지 않는다. 연결하면 되는 일이다.
- 조직과 내부 구조를 코드로 고정하지 않는다. 기반을 만들고 사용자가 꾸려 나간다.

세 문서의 자리는 이렇다. 이 문서가 구현 기준이다. [패러다임](ghost-paradigm.md)은 조직을 꾸리는 한 가지 권장 방식과 그 근거다. [실행 기반](ghost-execution.md)은 측정한 실패 원인과 품질에 관한 근거다. 뒤의 둘이 정한 구조는 코드가 강제하지 않는다.

## 1. 결론

1. **코드는 일의 종류를 모르고 일의 모양만 안다.** 누가 책임지는가, 어디서 실행하는가, 무엇에 닿는가, 무엇을 바꾸는가, 어떻게 확인하는가, 얼마를 쓰는가. 연재 소설인지 코드인지 생활 대행인지는 코드에 없다.
2. **기본 요소는 열 개다.** Ghost, 범위, 맡긴 일, 실행 환경, 기록, 능력, 계기, 정책, 자원, 계측. 조직의 모양, 역할, 연결할 서비스, 모델, 한도, 승인 기준은 모두 이 요소들 위의 데이터다.
3. **구성은 소유자와 Ghost가 대화로 한다.** 권한을 넓히는 변경만 소유자가 승인하고, 나머지는 누구든 바꾸고 되돌릴 수 있다.
4. **지금 코드에 고정된 다섯 가지를 연다.** 닫힌 도구 목록, 세 종류뿐인 계기, 도구 안에 든 승인 규칙, 상수로 박힌 한도, 메인만 가진 구성 도구.
5. **앞선 두 문서의 구조는 안내서가 된다.** 담당제, 역할 플레이북, 정본과 기준, 발행 단계는 메인이 조직을 꾸릴 때 읽는 지침과 예시로 남는다.

## 2. 가르는 기준

코드에 두는 것은 다음 셋 중 하나에 해당하는 것뿐이다.

- 어기면 되돌릴 수 없다. 효과를 실행 전에 기록하는 것, 자격 증명을 모델 맥락 밖에 두는 것, 같은 깨움을 한 번만 받는 것.
- 모델이 스스로 지키리라 기대할 수 없다. 완료 주장만으로 수용하지 않는 것, 자기 권한을 스스로 넓히지 못하는 것, 자원 한도.
- 어떤 구성에서든 필요하다. 지속과 재개, 계량, 격리된 작업 자리.

나머지는 데이터다. 지금 코드에 고정된 것과 그 결과를 적는다.

| 고정된 것 | 위치 | 결과 |
| --- | --- | --- |
| 고를 수 있는 도구 81개가 계약의 닫힌 목록이다 | `ghost-contract/src/entities.ts` `GhostTool` | 새 서비스에 닿으려면 코드를 고치고 릴리스해야 한다. 증권사 하나를 위한 `toss_read`가 그렇게 들어갔다 |
| 계기의 원천이 일정, PR, 메일 셋이다 | `ghost-contract/src/autonomy.ts` `ActivitySource` | 다른 것에 반응하려면 코드를 고쳐야 한다 |
| 승인 규칙이 도구마다 코드에 있다 | `connection_request`는 GET만 즉시, 나머지는 건별 승인. 메일 발신, 문서 제안, Mac 명령도 각자의 규칙 | 소유자가 한 번 정해 둘 수 없다. 실행 승인 262건의 응답 중앙값이 10초다 |
| 한도가 상수다 | 하루 깨움 12, 동시 실행 2, 트리 32, 재시도 2, 열린 목표 3, 하루 Ghost 생성 10 | 구성에 맞춰 바꿀 수 없다 |
| 구성 도구는 메인만 가진다 | `ghost_create` 등 `ghost.main` | 다른 Ghost는 자기가 맡은 범위도 꾸리지 못한다 |
| 모델과 PC 권한이 Ghost의 속성이다 | `Ghost.model`, `Ghost.hostExecution` | 권한이나 모델을 달리하려면 Ghost를 늘려야 한다. `Mac 관리`와 `심층`이 그렇게 생겼고 위임의 63%가 그 둘로 갔다 |
| 기본 실행 환경이 컨테이너다 | `sandbox/index.ts` | [실행 기반 3절](ghost-execution.md#3-컨테이너는-필요한가) |

같은 방식의 선례가 있다. Claude Code는 허용, 묻기, 거부 규칙을 설정 파일의 데이터로 두고 모델이 아니라 실행기가 집행하며, 능력은 MCP 서버와 스킬로, 지침은 파일로 붙인다([권한 문서](https://code.claude.com/docs/en/permissions)). 그 문서는 명령 문자열에 거는 규칙이 깨지기 쉽다고 경고하고 파일과 네트워크 경계는 샌드박스로 집행하라고 한다. 4절의 정책은 이 교훈을 따른다.

## 3. 기본 요소

| 요소 | 코드가 보장하는 것 | 데이터로 열어 두는 것 |
| --- | --- | --- |
| Ghost | 지속되는 정체성, 소유자와의 대화, 누가 맡았고 누가 판정했는지의 기록 | 몇 명인지, 각자 무엇을 맡는지, 지침 |
| 범위 | 맡긴 일, 결정, 계기, 기록, 경로, 규칙, 계측이 귀속되는 단위. 받을 Ghost 하나 | 무엇을 범위로 삼는지, 그 안의 구조 |
| 맡긴 일 | 계약, 환경, 실행 예산, 판정 순서, 트리, 새 맥락, 재개 | 크기, 나누는 방식, 무엇을 붙이는지 |
| 실행 환경 | 일마다 분리된 작업 자리, 쓰기 경계 | 그 Mac에 깔린 도구 |
| 기록 | 개정, 출처와 신뢰 표시, 충돌 검사, 맥락에 넣는 양의 한도 | 구조와 내용, 무엇을 늘 넣을지 |
| 능력 | 노출의 교집합, 자격 격리, 효과 기록, 읽기와 쓰기의 구분 | 무엇을 붙이는지 |
| 계기 | 한 번만 깨움, 커서, 새 맥락 | 무엇에, 언제, 어느 범위가 깨는지 |
| 정책 | 효과의 분류와 집행, 완화는 소유자만 | 어떤 효과를 누가 결정하는지 |
| 자원 | 계량, 한도를 아는 접수, 대기와 재개, 실행 시계 | 모델 대응, 한도, 우선순위 |
| 계측 | 결과, 비용, 뒤집힌 판정의 집계 | 그것을 보고 무엇을 바꾸는지 |

### Ghost

지금과 같은 종류의 지속형 봇이다. 달라지는 것은 Ghost에서 빠지는 것이다. 모델과 PC 권한은 Ghost의 고정 속성이 아니라 기본값이 되고, 실제 값은 맡긴 일과 범위에서 정해진다. 그래서 권한이나 모델 때문에 Ghost를 늘릴 이유가 없어진다. Ghost를 몇 명 두고 역할로 가를지 담당으로 가를지는 사용자가 정한다.

### 범위

화면에서는 프로젝트라고 부른다. 지금의 `Space`를 대신한다.

- 필드는 이름, 받을 Ghost, 경로 목록, 문서 금고 경로, 상태(진행·멈춤)뿐이다. 종류 필드가 없다.
- 범위가 없는 일과 대화는 전체 범위에 속하고 기본 Ghost가 받는다.
- 범위는 평평하다. 범위 안의 범위는 두지 않는다. 묶음이 필요하면 이름과 문서로 한다.
- 받을 Ghost가 하나인 것은 계기와 결과가 갈 곳이 하나여야 하기 때문이다. 한 Ghost가 여러 범위를 받는 것은 막지 않는다.

### 맡긴 일

지금의 수명주기에 네 가지가 더해진다.

- `scopeId`: 귀속.
- `attachments`: 이 일의 맥락에 넣을 문서 목록. 역할 지침, 평가 기준, 작품 설정 무엇이든 된다.
- `slot`: 모델 자리의 이름. 자원 절 참고.
- `retry`: 검사나 평가에 실패했을 때 어느 자리로 다시 돌릴지.

자기 자신에게 하위 일을 만들 수 있다. 실행은 늘 새 맥락이므로 같은 Ghost라도 다른 붙임으로 다른 일을 한다. 계약(`acceptance.checks`)과 판정 순서는 그대로다. 평가 대화는 산출물이 있는 작업 자리를 읽기 전용으로 열고 자기 자리에서 명령을 돌릴 수 있어야 한다. 지금은 요약과 게시된 파일만 읽는다.

### 실행 환경

[실행 기반 3절](ghost-execution.md#3-컨테이너는-필요한가)대로다. 기본은 작업 공간이고 Seatbelt로 쓰기를 그 일의 폴더와 워크트리에 묶는다. 컨테이너와 Mac 직접 실행은 일마다 고르는 선택지다. 어느 것을 고를 수 있는지는 정책이 정한다.

### 기록

두 저장소로 나눈다.

- **문서.** 소유자와 Ghost가 함께 쓰고 고치는 지속 문서다. 지침, 기준, 설정, 계획이 여기에 든다. 범위마다 문서 금고가 있고 형식은 PDC 2다(`pdc-markdown/1` 기본). 파일이 정본이고 소유자는 아무 편집기로나 고칠 수 있다. 기존 문서 어댑터(`integrations/documents.ts`)를 그대로 쓴다. 금고의 위치는 범위를 만들 때 정한다. 저장소 밖의 문서 폴더를 기본으로 권하고, 저장소 안의 `docs/`를 금고로 쓰는 것은 선택이다.
- **운영 기록.** Host가 쓰는 것이다. 진행 상태, 대화 검색 색인, 출처, 계측. 지금의 `memory.db`가 맡는다.

맥락에 넣는 것은 세 층의 붙임이다. Ghost에 붙은 것은 그 Ghost의 모든 대화에, 범위에 붙은 것은 그 범위의 모든 깨움과 일에, 일에 붙은 것은 그 일에만 들어간다. 층마다 분량 한도가 있고 넘치면 색인만 넣는다. 지금의 스킬, 환경 적응 메모, 프로젝트 문맥 머리말이 이 하나로 합쳐진다.

Ghost가 문서를 쓰는 것은 건별 소유자 검토가 아니라 정책이 정한다. 모든 쓰기는 누가 무엇을 근거로 썼는지와 신뢰 표시를 남긴다.

### 능력

코드 없이 능력을 더하는 길이 넷이다.

| 길 | 무엇 | 지금 |
| --- | --- | --- |
| 연결 | 자격 증명을 가진 HTTP API 계정 | 있다(`connection_register`, `connection_request`). 승인 규칙만 코드에 묶여 있다 |
| MCP 서버 | 표준 프로토콜로 도구 목록을 내주는 서버. 작업 공간에서 실행하거나 원격 주소로 붙는다 | 없다 |
| 작업 공간의 명령 | 그 Mac에 깔린 프로그램 | 컨테이너에서는 못 썼다 |
| 스킬 | 지침과 스크립트 묶음 | 있다 |

- 도구 이름은 열린 이름 공간이 된다. 내장 이름에 `mcp.<서버>.<도구>`와 `conn.<연결>`이 더해진다. Ghost의 허용 목록과 일의 범위 좁히기는 무늬로 적는다.
- 도구가 스스로 밝히는 성질은 믿지 않는다. MCP 규격도 신뢰한 서버가 아니면 도구의 주석을 믿지 말라고 한다([규격](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). 붙인 도구는 쓰기로 취급하고, 소유자가 읽기라고 표시한 것만 읽기가 된다.
- 내장 도구는 그대로 둔다. 새 영역을 위해 내장 도구를 더하지는 않는다. `toss_read` 같은 것은 연결로 옮길 수 있다.
- 도구가 많아지면 정의를 늘 싣지 않고 찾아서 싣는다. 정의 502개를 다 실으면 비용이 두 배 가까이 되고 지연 로딩은 그대로였다는 측정이 있다([Anthropic 비용 안내](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)).

일정 관리를 예로 들면 이렇다. 소유자가 캘린더를 붙여 달라고 하면 Ghost가 연결이나 MCP 서버 등록을 제안하고, 소유자가 승인하고, 기본 규칙에 따라 읽기는 바로 되고 쓰기는 소유자에게 묻고, 일정 변화에 깨는 계기를 범위에 건다. 코드는 바뀌지 않는다.

### 계기

Ghost를 깨우는 것을 하나의 모양으로 둔다. 원천, 조건, 받을 범위, 지시.

- 원천은 넷이다. 시각, 저장소의 새 커밋, 연결의 폴링(경로와 항목 식별자, 커서), Ghost가 스스로 정한 다음 시각. 지금의 예약, 자동 활동, 자율 계획이 여기에 든다. PR과 메일 전용 원천은 연결 폴링의 한 경우가 된다.
- 깨움은 늘 새 맥락에서 돈다. 받을 Ghost의 직접 대화에 쌓지 않는다([실행 기반 4절](ghost-execution.md#4-실행-기반-설계)).
- 스케줄러는 지금처럼 하나다. 계기는 행이고 실행기는 늘지 않는다.
- 읽기만 하는 계기는 Ghost가 건다. 밖으로 나가는 효과를 허용받는 상시 계기는 소유자가 승인한다.

### 정책

4절.

### 자원

- **모델 자리.** 맡긴 일, 깨움, 평가는 자리의 이름을 요청한다. 자리를 어떤 모델과 대체 모델에 대응시킬지는 설정이다. 자리의 이름과 수도 사용자가 정한다. 코드는 어느 모델이 강한지 모른다.
- **한도 인지.** 제공자별 한도 상태, 접수 우선순위, 대기와 재개, 한도 오류를 Ghost의 멈춤으로 세지 않는 것([실행 기반 4절](ghost-execution.md#4-실행-기반-설계)).
- **실행 시계.** 일하는 시간만 세는 실행 예산과 소유자가 정했을 때만 있는 기한.
- **한도.** 하루 깨움, 동시 실행, 트리 크기, 재시도 횟수는 설정이고 범위별로 덮어쓸 수 있다. 지금의 상수가 기본값이다.

### 계측

구성을 사용자가 정하므로 그 구성이 잘 도는지 알 수단이 기반에 있어야 한다. Host가 범위, Ghost, 모델 자리, 규칙별로 다음을 집계하고 소유자와 Ghost가 읽는다.

- 맡긴 일의 완료율과 반려율, 끝낸 일 하나의 비용과 시간.
- 소유자가 뒤집은 평가 판정의 수.
- 규칙별로 소유자가 고치지 않고 승인한 횟수와 거절한 횟수.
- 한도로 대기한 시간, 같은 실패의 반복.

## 4. 정책

밖에 닿는 모든 행동은 효과이고, 효과마다 누가 결정하는지를 규칙이 정한다. 규칙은 데이터이고 집행은 코드다.

### 코드가 정하는 축

효과를 분류하는 축은 고정이다. 도구 이름이나 명령 문자열이 아니라 닿는 곳으로 분류한다.

| 축 | 값 |
| --- | --- |
| 대상 | 작업 자리, 범위의 경로, 범위 밖의 Mac, 문서 금고, 연결(어느 것), 브라우저(어느 출처) |
| 되돌림 | 가능, 불가. 도구가 밝히지 않으면 불가 |
| 바깥 | 기기 안에 남는다, 제3자에게 나간다 |
| 금액 | 있으면 그 값 |
| 맥락 표시 | 이 일이 신뢰할 수 없는 입력을 읽었는가, 비공개 데이터를 읽었는가. Host가 추적한다 |

### 규칙

규칙 하나는 조건과 결정이다. 조건은 범위, Ghost, 도구 무늬, 위 축의 값이고, 결정은 넷 중 하나다.

- **허용.** 기록만 남긴다.
- **평가 후 허용.** 규칙이 이름 붙인 평가자(Ghost나 모델 자리)가 본다.
- **소유자.** 결정 카드를 연다.
- **거부.**

여러 규칙이 맞으면 거부, 소유자, 평가, 허용 순으로 엄한 쪽이 이긴다. 더 구체적인 허용이 넓은 소유자 규칙을 뚫지 못한다. 규칙에는 하루 횟수와 금액 한도를 붙일 수 있다.

### 기본 규칙표

설치할 때 들어 있는 데이터이고 소유자가 고친다.

| 효과 | 결정 |
| --- | --- |
| 작업 자리 안의 쓰기와 실행 | 허용 |
| 범위 저장소의 워크트리 브랜치 커밋 | 허용 |
| 문서 금고 쓰기 | 허용. 개정이 남는다 |
| 연결과 붙인 도구의 읽기 | 허용 |
| 본 브랜치 통합 | 평가 후 허용 |
| 연결과 붙인 도구의 쓰기 | 소유자 |
| 제3자에게 나가는 것(메일, 게시, 댓글) | 소유자 |
| 금액이 있는 것 | 소유자 |
| 범위 밖 Mac을 바꾸는 것 | 소유자 |
| 신뢰할 수 없는 입력과 비공개 데이터를 모두 읽은 일의 바깥 행동 | 소유자 |

마지막 줄이 [Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)다. 코드에 든 것은 맥락 표시를 추적하는 기제이고, 그것으로 무엇을 막을지는 규칙이다.

지금의 동작은 이 표로 옮겨 적을 수 있다. 메인의 선검토는 평가자가 메인인 규칙이고, 시간이 지나면 추천안을 따르는 것은 그 규칙의 선택 항목이다. 그래서 정책 엔진은 동작을 바꾸지 않고 들여올 수 있고, 그 뒤에 소유자가 규칙을 고친다.

### 규칙을 바꾸는 사람

- Ghost는 규칙을 제안한다. 근거로 계측을 붙인다. 예: "이 계정의 게시는 20번 연속 고치지 않고 승인됐다."
- 완화는 소유자만 확정한다. 강화는 그 범위를 받는 Ghost도 한다.
- 규칙마다 개정과 적용 횟수가 남는다. 결정 카드에는 어느 규칙 때문에 물었는지가 보인다.

[실행 기반](ghost-execution.md)이 적은 발행 단계(초안만, 승인 후 발행, 자율 발행)는 코드의 단계가 아니라 이 규칙을 차례로 완화하는 한 가지 방식이다.

### 바닥

규칙으로 바꿀 수 없는 것이다. 모두 지금의 원칙이다.

- 비밀 값은 모델 맥락에 들어가지 않는다.
- 효과는 실행 전에 기록하고, 결과를 모르는 바깥 효과는 자동으로 다시 실행하지 않는다.
- 권한은 대화 종류, Ghost, 일, 연결 허용의 교집합을 넘지 않는다.
- Ghost는 자기 권한을 스스로 넓히지 못한다.
- 완료 주장만으로 수용하지 않는다.

## 5. 누가 꾸리는가

- 구성 명령은 모두 Owner API의 명령이면서 Ghost의 도구다. 범위 만들기, Ghost 만들기와 고치기, 문서와 붙임, 계기, 규칙 제안, 연결 등록 제안, 자리 대응 제안.
- 구성 권한은 범위를 따른다. 전체 범위를 받는 기본 Ghost는 범위와 Ghost를 만들고, 범위를 받는 Ghost는 자기 범위 안을 꾸린다. 지금은 기본 Ghost만 구성 도구를 가진다.
- 권한을 넓히는 변경은 소유자의 결정 카드를 거친다. 새 연결과 자격 사용, 범위에 경로 추가, 규칙 완화, Mac 직접 실행, 밖으로 나가는 상시 계기, 한도 상향, 비용이 달라지는 자리 대응이 그렇다.
- 그 밖의 변경은 바로 적용된다. 범위와 문서의 구조, 붙임, 일을 나누는 방식, 읽기만 하는 계기, 규칙 강화.
- 모든 구성 변경은 누가 왜 바꿨는지와 함께 개정으로 남고 되돌릴 수 있다.

빈 설치에는 기본 Ghost 하나, 기본 규칙표, 기본 한도만 있다. 범위도 역할도 없다. 조직은 소유자와 기본 Ghost의 대화에서 생긴다. 기본 Ghost는 그때 안내서를 읽는다. 안내서는 스킬 하나이고 [패러다임](ghost-paradigm.md)과 [실행 기반](ghost-execution.md)의 권장 구성과 측정 근거를 담는다. 범위마다 받을 Ghost를 두는 방식, 역할을 붙임으로 두는 방식, 일 전에 계약을 쓰는 방식, 연재와 영상과 SNS의 문서 구조 예시가 거기에 있다. 따르지 않아도 된다.

## 6. 화면

기본 요소의 일반 화면만 둔다. 범위 목록, 범위 하나(대화, 맡긴 일, 결정, 문서, 계기, 규칙, 계측), Ghost, 범위별로 묶인 확인할 일, 설정(연결, 모델 자리, 한도). 업무 영역별 화면은 만들지 않는다. 영역에 맞는 표시는 Ghost가 `present_ui`와 문서로 만든다.

## 7. 앞선 문서의 항목이 가는 곳

| 항목 | 가는 곳 |
| --- | --- |
| 범위와 귀속, 일의 붙임과 모델 자리, 자기 위임 | 코드 |
| 한도 인지 접수, 실행 시계, 반복 차단, 새 맥락 깨움 | 코드 |
| 작업 공간 환경 | 코드 |
| 계약, 실물을 여는 평가 환경, 실패 시 다른 자리로 재시도 | 코드(기제). 누가 평가하고 어느 자리로 올릴지는 데이터 |
| 산출물 연결과 기억 색인의 결함 | 코드 |
| 범위마다 담당 하나, 역할은 Ghost가 아니라 지침 | 안내서. 코드는 "범위에 받을 Ghost 하나"만 안다 |
| 역할 목록, 지금 Ghost 26명의 재편 | 소유자와 기본 Ghost가 대화로 |
| 목표 개수, 일의 크기, 평가자 선택 | 설정과 안내서 |
| 정본, 기준, 채널, 리듬과 업무별 표 | 안내서의 문서 구조 예시 |
| 발행 단계, 전결 표 | 규칙의 예시 |
| Rule of Two | 맥락 표시 기제와 기본 규칙 한 줄 |

## 8. 위험과 한계

- **범용 도구는 전용 도구보다 쓰기 어렵다.** 연결에 대고 API를 직접 부르는 것은 맞춤 도구보다 모델의 실수가 잦다. 도구 설명의 질이 결과를 크게 가르고, 설명을 다듬는 것만으로 완료 시간이 40% 줄었다는 보고가 있다([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). 그래서 연결마다 사용 안내 문서를 두고 실패에서 고쳐 나가야 하며, 형식이 있는 도구가 필요한 곳은 MCP 서버가 맞다.
- **빈 설치는 막막하다.** 구조를 강제하지 않으면 처음에 무엇을 할지 모른다. 안내서와 기본 규칙표가 그 자리를 메운다. 안내서의 질이 첫 경험을 정한다.
- **규칙이 늘면 소유자가 이해하지 못한다.** 축을 고정하고, 엄한 쪽이 이기게 하고, 결정 카드에 적용된 규칙을 보여 주는 것이 완화책이다. 규칙 수 자체를 계측한다.
- **Ghost가 완화를 조른다.** 제안에는 계측 근거가 있어야 하고 거절된 제안은 일정 기간 다시 올리지 못한다. 기간은 설정이다.
- **도구가 늘면 고르는 정확도가 떨어진다.** 비슷한 것이 많을수록 급격히 떨어진다는 측정이 있다([Li, 2026](https://arxiv.org/abs/2601.04748)).
- **붙인 서버와 명령은 새 공격면이다.** MCP 서버는 작업 공간의 경계 안에서 돌리고, 그 도구의 쓰기는 기본 규칙에서 소유자에게 묻는다.
- **자체 증거가 없다.** 이 분리가 Ghost에서 더 낫다는 측정은 없다. 9절의 시나리오가 통과하는지가 첫 검증이다.

## 9. 수용 기준

기반이 맞게 만들어졌는지는 Host 코드를 고치지 않고 다음을 할 수 있는지로 본다.

1. 캘린더 서비스를 붙이고, 일정이 바뀌면 깨어나 초안을 쓰게 한다.
2. 연재 작품 범위를 만들어 문서 구조와 평가 기준을 정하고, 회차를 쓰고 평가받는다.
3. SNS 계정의 게시를 건별 승인에서 규칙으로 완화했다가 되돌린다.
4. ffmpeg를 쓰는 영상 편집 일을 작업 공간에서 끝내고 파일 검사로 판정받는다.
5. 같은 설치에서 역할 Ghost 방식과 담당 방식을 각각 꾸려 본다.
6. 모델 자리의 대응을 바꿔도 범위, 문서, 규칙, 계기가 그대로 돈다.

실패 지표는 [실행 기반 12절](ghost-execution.md#12-검증-지표)을 그대로 쓴다.

## 10. 구현 순서

앞의 것이 뒤의 것의 전제다. 0~3은 [실행 기반](ghost-execution.md)의 것이고 구성과 무관하게 효과가 있다.

0. **결함.** 산출물 최신 연결, 검증 중 만료 제거, 한도 오류가 독촉과 시계를 쓰지 않게, 기억 색인 충돌 조사.
1. **자원.** 한도 상태와 접수 우선순위, 대기와 재개, 실행 예산과 기한의 분리, 반복 차단. 한도 상수를 설정으로.
2. **맥락.** 깨움과 결정 검토의 새 맥락, 세 층의 붙임.
3. **작업 공간.** Seatbelt 프로필, 워크트리 기본값, 프록시, 평가 대화의 읽기 전용 열람.
4. **범위.** `spaces`를 범위로, 맡긴 일·결정·계기의 귀속, 모델 자리. 저장 형식이 바뀐다.
5. **정책.** 효과 분류와 규칙 엔진. 도구마다 든 승인 규칙을 기본 규칙표로 옮긴다. 처음에는 지금과 같은 동작이 나오게 한다.
6. **능력.** 열린 도구 이름, MCP 연결, 연결의 읽기 표시, 도구 지연 로딩.
7. **계기.** 원천의 일반화와 연결 폴링.
8. **구성 도구와 계측.** 범위를 받는 Ghost의 구성 도구, 구성 변경의 개정, 집계.
9. **안내서.** 스킬로 쓴다. 지금 Ghost 26명과 프로젝트 9개의 재편은 소유자와 기본 Ghost가 그 안내서를 놓고 대화로 한다. 저장소 9곳에 추적되지 않은 채 남은 문서 163개의 처리는 삭제가 포함될 수 있어 소유자가 따로 정한다.

4, 5, 6은 저장 형식이나 보안 경계를 바꾼다. 백업, 쓴 모델과 다른 계열의 독립 검토, 소유자의 마이그레이션 승인이 필요하다.
