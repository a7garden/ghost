# ADR-005 — owned fake browser child and durable host intent

2026-10-02. This unit exercises Ghost's browser core boundary against a Rust fake stdio child. The actual OxiBrowser executable, real sites, credentials and new persistent external access are not used. There is no production browser launch or credential/account UI. `browser-fixtures` is required to construct the child host and the trusted fixture control; the default artifact cannot launch this fixture or mint browser grants through this API. The test fixture executable is not a dependency of the default single executable.

Read-only contract references: OxiBrowser `docs/ghost-mcp.md` and `crates/oxibrowser/src/mcp/ghost.rs`, owned by separate browser task 01a0fba5-68b8-7789-a41c-4ed98606f0bf. The core implements initialize and bounded newline JSON-RPC tools/call, explicit tab IDs, `_meta` correlation, snapshot refs, cancellation and conservative uncertain outcomes. No browser repository file was written. Upstream test reports are not reproduced/claimed as Ghost test results. The latest upstream source documents native DOM validation/event dispatch independent of page selector/Event/prototype APIs, but still synthetic main-document events with isTrusted=false and no OS input/full web compatibility guarantee. Its reported 124 tests were not rerun here. Existing envelope/correlation/ref contracts remain compatible; actual child integration still needs separate local-fixture execution.

## Authority and process ownership

`TrustedFixtureControl` has private profile UUID/path binding and no serde input route. Its explicit local fixture constructor can approve/revoke scoped operations or acknowledge a stopped session without replay. `BrowserCommand` accepts only new/tabs/navigate/snapshot/click/fill/close, rejects extra fields, and cannot represent approval, handoff, reconciliation or resume. No grant is derived from page text, model text or a result label. This separates trusted host control from agent/page input; it does not authenticate a human or provide a finished trusted input UI.

Fixture grants use the existing `grants` table with operation `browser_fixture` and `fixture://local/<session>` target plus a session/operation binding table. They grant no filesystem or real network access. Existing `ProfileStore::revoke` also revokes them. Check active scope before spawn and every new forwarded request. Admission errors (denied/revoked/session mismatch/invalid ref or input) return an error before intent or child bytes and leave the task queued; pre-dispatch cancellation uses the existing terminal cancelled/outbox contract. The future dispatcher must handle these errors explicitly rather than claim execution.

One owned Child handle per Ghost/session, one profile writer. Cleared configured child environment (macOS frameworks may add their own __CF_USER_TEXT_ENCODING key), direct executable invocation, no shell or inherited authentication/config, stderr discarded, no existing process/profile attach. Initialize binds the ephemeral browserSessionId to the child. Historical PID is diagnostic data and is never sufficient to attach, kill or resume a process. Only the owned Child handle is killed/waited; shutdown is bounded at one second. Drop closes its own child. Abrupt host death closes stdio; the finite fixture exits after its bounded delay/EOF. A process boundary itself is not an OS sandbox.

## Intent, receipt and recovery

One browser command is one existing Ghost task in its session. This unit is a library host API, not a browser CLI dispatcher. Reject tasks carrying filesystem actions. Persist running task, existing effect row (`action=browser`), request ID, immutable command JSON, profile/session/task UUIDs, child scope and audit **in one transaction before stdin bytes**. Browser-local IDs alone never authorize restart replay. A task can have only one browser intent; a different request ID cannot bypass that uniqueness. An identical durable duplicate returns the stored receipt, including failed/uncertain states; changed task/payload is an ID conflict. A duplicate is never forwarded or used to rebuild a fresh child's tab/ref cache.

Validate bounded UTF-8 JSON line (65,536 bytes), envelope ID/version, profile/task/request/child `_meta`, result state and text/structuredContent agreement. Quarantine the structured result as untrusted data. Raw transport/protocol failure text is not promoted to authority. New tab IDs are tracked and never reused after close. Action refs must appear in the most recent accepted snapshot for that exact owned child/tab, have the child namespace and a fillable flag for fill. Before snapshot/navigation/action/close attempts, invalidate observations for that tab. After any action, observe again. Only `about:blank` navigation and values up to 4 KiB are admitted in this fixture unit; all real URLs are denied before forwarding.

Validated success commits task/effect/receipt/outbox/audit atomically, with exact update counts. A typed definitive child error requires both `mayHaveActed:false` and `restartRequired:false`; it is terminal failed and never retried. All malformed/forged/oversized responses, EOF/crash, lost receipt, timeout/cancel, `mayHaveActed:true` or restartRequired become uncertain. Stop the owned child, block the session and never apply a late result to a future task. An interrupted intent's canonical task/effect recovery is the existing store's authority; `browser::recover` marks its browser receipt uncertain and session blocked. Missing final commit never creates a success outbox.

Reopening after a lost result cannot automatically start another child for that session. Trusted fixture reconciliation first recovers pending tasks/effects, records `do_not_replay` for uncertain requests and only then permits a new empty child. The old task/effect remains uncertain and terminal. Trusted handoff stops the owned child, clears refs and persists suspension. Resume requires that separate local control and a reason; old tabs/refs never migrate. This is fixture lifecycle validation, not a shared browser/human handoff UI or evidence of actual human approval.

## Deliberate limits

No live OxiBrowser launch, production site interaction, cookies/passwords/credential store, domain/subresource policy, OS containment for real browsing, authentication/UI, encrypted IPC, model tool integration or 24-hour scheduler. Host API is synchronous and runs outside an active Tokio runtime. Per-child calls are serialized by mutable ownership; durable replay covers duplicates, but no parallel socket/client fanout is implemented. Browser busy/limit/RPC errors conservatively end uncertain rather than minting IDs or retrying. A completed transport receipt does not prove a desired business outcome. Financial decisions/payments/sharing remain outside this capability.
