# Owner task contracts and independent verification

This is an opt-in Host API path for an authenticated Owner to install a reusable task template and select immutable inputs for an actual conversation turn. Ordinary unconfigured chat does not receive automatic verification or new delegation authority. The A04 comparison scenario installs its own fixture package; product comparison is not a Host built-in verifier.

`task.contract.register` accepts the exact `ghost_id`, `conversation_id`, bounded `id` and `content`. The content pins instructions, disclosure, input/output JSON schemas, input/output eligibility contracts, required capabilities, output filename and verifier asset. Updates require the actual previous template revision in the envelope. The response returns an immutable `{id, revision, digest}` reference. Verifier assets must name the accepted image and `/bin/sh`, contain at most 256 KiB, and match their SHA-256. Schema remote references are forbidden.

An authenticated `conversation.input` can additionally supply `task_contract: {template, mode, input}`, where `mode` is `direct` or `delegate`. The Host validates the input against the selected template and joins its disclosure with the turn. The immutable instance binds the actual Owner command digest, turn, conversation, template and input digest. It is not a model-provided approval claim. The current turn inspection returns only an opaque task reference and task metadata; it does not duplicate the raw input. Before each Owner generation, the runtime places only the freshly validated reference, mode and input digest into its ephemeral header. Exact turn/identity, active state and cancellation are checked again at actual public, local and registered provider admission. A failed inspection is not treated as absent selection; a descriptor change blocks that request. No descriptor is persisted as ambient conversation authority.

The Owner-turn model can inspect this optional contract with `task_contract_inspect`, then call `goal_create` with only `task_contract_ref`. The Host resolves the prompt and verifier. The model cannot mix this form with prompt, input, verifier, acceptance or actor overrides. When the actual Owner turn selected a contract, a plain prompt/spec Goal request is rejected rather than bypassing that selection. An assignment receives the input through a Host-staged `owner-input-<digest>.json` file in its own Work workspace.

For delegate mode, `work_inspect` exposes a target-free template reference. The primary Ghost selects a ready bot by purpose and exact eligibility metadata, then supplies only the template reference, parent Work and selected Ghost ID. Admission checks the current lifecycle, independently accepted definition, exact contracts/capabilities and current native computer route. The chosen definition is pinned to the child Work. A missing eligible bot blocks this responsibility; it does not authorize another bot, broader scope or a new verifier. Fixed-target delegation contracts remain available separately.

The primary must receive one independently accepted eligible child result before its own final output can be accepted. Each producer must publish its own artifact and complete its exact Work. Producer shell success, fake verifier files or an assistant answer do not establish acceptance.

## Verifier boundary

The existing Host driver launches a deterministic native verifier in a separate execution compartment on the already accepted computer. Only the Host-reopened immutable script, Owner input and published output are mounted at `/inputs`, read-only. Producer home files and import paths are absent. The image, interpreter and invocation are fixed; the environment is cleared, the root filesystem is read-only, networking is disabled, and writable scratch is disposable `/tmp`. The current bound is 30 seconds, one CPU, 256 MiB and 64 KiB combined output.

The durable plan pins the script, input, output, template, policy, Work revisions, execution and Host epoch. Work-memory and publication source authority is refreshed before and after verifier I/O. An exact freshly checked publication revision is compared under the writer lock; dependency growth cannot be recaptured as if it were checked. Cancellation, source revocation, policy change or epoch fencing withholds acceptance.

A pending receipt is written before verifier I/O. An unknown stop retains the native lease and is never automatically re-executed. A known stopped success can recover an interrupted acceptance commit only after fresh source checks, without running the guest again. Failed and unknown executions are not retried automatically. A durable round-robin cursor prevents permanent preflight or acceptance blockers from starving later Work. Generic synchronous `work.verify` cannot accept a cached task-verifier receipt; only this freshly checked driver path can.

## Conversational bot derivation

An exact Owner request such as `방금 우리가 수행한 작업을 봇으로 만들어줘` (also `이걸 봇으로 만들어줘`) remains create-from-task intent and requires at least one current independently accepted source Work from that actual Owner conversation. The model cannot label an unfinished or foreign task as a completed source. The successful acceptance command must precede the actual Owner creation command in the durable journal; wall-clock time is not used. Candidate bytes pin the exact source Work revision, immutable Acceptance, acceptance command identity and digest. The acceptance receipt must match the stored proof.

A separate full-match request such as `이 요구사항으로 봇을 만들어줘` or `create a bot from these requirements` authorizes requirements-based preparation without a completed source. The Host derives this mode from the actual committed Owner text, not a model argument or workspace-wide permission switch. Both forms retain the fixed Owner evaluator, current cancellation/epoch checks, readiness checks and immutable candidate identities.

## SDK inference boundary

Pi 1.1.0 can report a `beforeRequest` hook exception and still proceed toward its model adapter. The provider admission check therefore independently revalidates the current Owner observation; throwing from the header hook alone is insufficient. Tests exercise both a denied receipt and thrown inspection, plus changed reference/mode/input digest, with valid positive controls for every configured transport.

SDK compaction invokes `Models.completeSimple` directly, including after a summarize checkpoint reopens. A private wrapper recognizes the pinned SDK's no-tool summary call shape and binds its purpose to that invocation with `AsyncLocalStorage`. Its model request still receives fresh Owner/disclosure/source validation; memory-derived or Work-derived history remains blocked by the existing memory context guard. Only this clean summary can proceed without a generation-header observation. The later generation must acquire and match its own fresh selected descriptor. Summary text and persisted history do not receive that descriptor.

The strengthened A04 harness uses the original A20 corpus only for the completed seed task and fixed held-out evaluation. Its two reuse requests carry separate `tests/fixtures/a04/reuse-one.json` and `reuse-two.json` source artifacts, with disjoint source/product IDs, actual changed facts and distinct digests. Both the new immutable Owner input read and the exact accepted child artifact path/SHA read by the primary are checked. The final evidence records the source Work revision and immutable acceptance command before the natural Korean creation command in journal order. The fixed generic Owner verifier package is unchanged; expected outputs exist only in the separate test oracle.

The first actual A04 trial is retained as failed: one local call (3,770 input / 163 output tokens) produced an advisory request for product names and no Goal. Both source fences were clean. The contained context fix has component tests; it does not establish actual product-scenario acceptance until a separate coordinated trial passes.

## A04 fixture package

`src/host/a04_product_fixture.rs` is test-only Owner-installed code. Its comparison checker derives every result from arbitrary schema-validated input sources and criteria, rather than choosing from named cases or embedding expected outputs. It uses the frozen A20 public fictional-product corpus; it is not live purchase research.

The accepted image includes Perl but lacks a JSON library. The fixture explicitly bundles the vendored pure-Perl `JSON::PP.pm` and `JSON::PP::Boolean` sources under `tests/fixtures/a04/vendor/JSON/`, copied byte-for-byte from the local system distribution (`/System/Library/Perl/5.34/JSON/`). Their original license text is retained in the packaged bytes; both are distributed under the same terms as Perl itself. The entire shell package, including these dependency bytes, is pinned by the Owner verifier digest. Both dependency files and the package are included in the trial source manifest; no package installation, dependency download or fallback occurs. Expected answers remain in the independent test oracle and never enter model prompts or verifier registration.

The creation recognizer is a bounded full-match grammar, not general intent inference. It also accepts the completed-task forms `방금 수행한 작업을 봇으로 만들어줘` and `방금 완료한 작업을 봇으로 만들어줘`, with the corresponding `만들어주세요` ending. Quoted examples, translations, negations, conditions, future modifiers and unmatched wording do not grant creation authority. Unsupported requests report unrecognized intent instead of silently acquiring a broader grant.
